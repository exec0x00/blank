# Permanent workspace conversation cleanup

`cleanupWorkspaceConversationState(ctx, request)` consumes the internal `WorkspaceArtifactCleanupRequest` from the workspace lifecycle. Call it only during permanent deletion or a 30-day trash purge, after the lifecycle has admitted removal and retired the workspace root. Ordinary archive, trash, restore, login and restart do not erase conversations.

The caller keeps its existing workspace removal gate. The leaf never reacquires that gate, resolves the missing workspace root, initializes an agent/model, or sends a provider request. Signed file-rewind cleanup must run first, while its canonical conversation and backup ownership proofs remain available. Attachment/image and checkpoint leaves keep their separate ownership boundaries; this leaf consumes none of their metadata.

The leaf covers full conversations and delegated histories, private provider input, delivered and waiting input copies, embedded image data, exact turn journals, history backups, review snapshots, delegated final reports/notifications, goal objectives, title metadata and context sidecars. Shared conversation/agent/goal/title indexes and the inline `agent-changes` source snapshots are filtered through the actual store's serialized key queue. Only matching workspace-owned entries are removed. Personal configuration, model profiles, accounts, encrypted credentials, skills and workflows are outside this leaf.

Generated-memory cleanup covers extraction records and edit chains, extraction summaries/jobs, consolidated artifacts/manifests/jobs/heads and the deleted workspace's startup metadata. It runs directly against validated files, without a memory service recovery pass. Content-free generation barriers, source invalidations, deletion markers, request-budget charges and uncertain-attempt receipts remain; removing those could admit stale results or repeat model spending.

Every source file must be an ordinary, pinned, bounded file with matching filename/body identity. Legacy journals additionally require an exact saved turn reference. Modern journals include their own versioned `threadId` and `workspaceId`, so a failed fork cannot lose all ownership evidence. Conflicting ancestry, unsafe links, arbitrary stored file keys, unowned legacy content, changed generations, oversized records and unresolved partial writes stop cleanup with a retryable failure. No namespace prefix alone grants deletion authority.

A signed, content-free receipt records the exact owned IDs and source hashes before destructive work. Per-thread deletion tombstones are permanent. The receipt allows a fresh process to finish deletion after canonical parent files have already disappeared. Validated conditional-write recovery bundles also supply ownership and exact legacy references when they are the only remaining conversation source; their separately owned cleanup helper runs under the same per-source store queues. Journals and derived copies are removed before canonical threads, and a final scan checks that no newly arrived owned content or recovery bundle was overlooked.

Already-constructed engines, naming helpers, goals, delegated coordinators and memory workers are fenced and drained. Full persistence promises are tracked from method entry, including creates outside engine admission. Memory mutation admission and lazy recovery are held during the attempt; existing unrelated extraction publication remains scoped. Every live instance retains its own cleanup registration. Startup memory's shared document is drained and reloaded after cleanup so stale cached reports cannot be written back.

Conversation scans admit at most 100,000 directory entries, 32,768 owned references, 32 MiB per source record, 128 MiB per shared aggregate and 2 GiB of total reads within a 120-second file-work budget. Each runtime drain has a 15-second timeout. Memory cleanup has its separate published limits (120,000 directory entries, 256 KiB records, 1 GiB reads and a 60-second budget). Reaching a bound leaves an incomplete deletion for retry rather than broadening its scope.

The native bucket is not a distributed compare-and-swap store. Pinned paths, exact readback, generation checks and serialized app writers protect the supported single-runtime lifecycle; they do not grant an uncooperative external writer permission to reuse deleted IDs. Detected outside edits remain visible failures, and ambiguous retained data is never silently called deleted.

Verification is source-authored and pending the coordinator's runtime slot: `workspace-conversation-cleanup.test.ts`, `workspace-conversation-cleanup-api.test.ts`, `workspace-conversation-cleanup-writers.test.ts` and `workspace-memory-cleanup.test.ts`. These use real temporary files, actual lifecycle/API paths and controlled writer barriers. No hosted acceptance or complete crash-fault coverage is claimed by this document.
