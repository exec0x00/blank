## Minimal mitigation boundaries

**Accounts need independent authoritative records.** Store public metadata and the encrypted PAT together per account, with durable disconnection state. A shared list can be derived from those records; it must not be the only surviving source. Preserve the existing encryption key and credentials during migration, prefer existing new-format state over delayed legacy imports, and do not resurrect disconnected identities from leftover legacy ciphertext. This addresses unrelated account creation without introducing a synchronous remote request in ordinary account lookups. The coordinator has assigned this correction to the GitHub module owner, who is also evaluating immutable observed-version/disconnection operations for explicit same-account conflicts. This document does not claim that pending correction has shipped.

**Session semantics currently require one active runtime.** The smallest honest immediate boundary is one `AuthService` authority while the Space is serving mutations, with orderly replacement and preserved secrets. Matching source/runtime SHA does not prove this when multiple rollouts use the same source. An authenticated per-boot instance identifier would provide useful evidence of which runtime answered requests; it would not itself exclude other writers.

If session persistence must tolerate unrelated logins across instances, use one durable record per token digest and a revocation marker that remains until expiry. Initialization should load these records rather than rewrite a complete stale snapshot. Old password epochs remain invalid. Distinct logins then do not share a mutable aggregate; logout must prevent a stale active record from becoming valid again. Live cross-instance revocation still needs an explicit consistency boundary, because current authentication and WebSocket checks are in memory. Do not replace server-side membership with acceptance of every correctly signed cookie.

**Conversation listing can be repaired from existing records.** Validate bounded `thread-<id>.json` records and use them to repair missing summary entries, preserving workspace, parent, root, archive, and interruption semantics. Use bounded reads and an in-memory/derived summary view so normal navigation does not repeatedly parse every full conversation. Deletion needs a durable tombstone before an orphan scan is introduced: current removal deletes the summary before the full record, so blindly importing remaining files after interruption could resurrect intentionally deleted threads. Direct known-ID loading and background persistence must honor the same tombstone. Keep live runs and writes to one conversation under the explicit single-runtime boundary; rebuilding a list does not solve competing model/tool execution.

The upstream native filesystem documents eventual remote visibility and local-only advisory locks, with no coordination of locks across clients. The application therefore cannot claim a distributed mutex from a lock file or `flock`, or an atomic remote compare-and-swap from a metadata check followed by rename. Advanced writes also flush asynchronously; a local completed save is separate from evidence that remote storage has received the bytes. These are the reasons to use independent records, meaningful recovery checks, and stated runtime bounds. [Upstream consistency model](https://github.com/huggingface/hf-mount#consistency-model), [upstream capabilities](https://github.com/huggingface/hf-mount#features).

No live account/session/thread writes, filesystem lock protocol, remote CAS, or production code changes were performed for this review. The review was limited to source, existing verification scope, the already-observed workspace failure, and the upstream filesystem documentation.

## Subsequent corrections in the working source

The earlier table records the representation that prompted this audit. The GitHub owner subsequently implemented immutable per-account metadata/encrypted-token versions and permanent disconnect markers, documented in [GITHUB_PERSISTENCE.md](./GITHUB_PERSISTENCE.md). Different accounts no longer replace a common credential map. Compatible identical-token versions can coexist; incompatible heads fail closed until an explicit verification resolves the versions it observed. Review exposed an additional publication/rollback race: a same-token caller could acknowledge another writer's provisional record without owning a durable version. Both initial-connection and token-replacement regressions reproduced the loss; the fix requires every successful connection request to publish its own complete version. The owner reports 97 targeted checks passing after that correction. Native visibility, ambiguous same-identity heads, and rollback to obsolete readers retain their documented boundaries.

The authentication owner replaced whole-map session writes with per-cookie-digest grants and separate revocation records in expiry-day directories under `auth-sessions-v2`. REST authorization reads current membership and revocation state; it does not authorize from a process-local positive-membership map. Any revocation entry, including a malformed value, directory, or dangling symlink, denies access. Observed revocations are pinned locally, and local logout notifies streams before durable I/O. Bounded expiry cleanup retains iteration progress and uses no-follow directory descriptors so a replacement symlink cannot redirect deletions. Three concrete review findings—missed logout notification after observation eviction, cleanup starvation, and cleanup redirection—were corrected and covered by regression cases. The owner reports 103 targeted checks passing across authentication, concurrency, settings, and provider tests; the API performance behavior suite also passes on the updated working source.

Session migration is a one-way per-epoch cutover. Visible, valid legacy sessions are imported before a permanent completion marker is written. New code never rewrites the aggregate and never imports later obsolete snapshots once the marker exists. Aggregate-only runtimes must be retired orderly; this is not an exclusion protocol, a guarantee of cross-client visibility, or proof that native asynchronous uploads have completed remotely.

Password/signing-material rollback is an explicit configuration boundary. Restoring exactly previous password and signing material can make still-unexpired, unrevoked grants from that matching epoch valid again. Existing revocation records remain authoritative. The epoch is not a global monotonic revocation registry, and the implementation makes no claim that a configuration rollback permanently invalidates every older cookie.

The terminal adapter's five-second bound limits authorization-proof age. It does not eliminate the native mount's remote-visibility delay; input/output are gated while revalidation awaits. These working-source changes still need the coordinator's full-release hosted checks, including a pre-existing cookie, fresh login/logout, and the final API/terminal profile. The successful hosted API evidence for `a785470ccb66be1e8c7992905be7663d1332d9b3` covers the earlier workspace-registry hotfix, not these later account/session changes.
