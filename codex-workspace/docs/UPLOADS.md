# Workspace uploads through the public transfer bucket

Workspace file bytes travel from the browser directly to Hugging Face Xet storage. The Node app reserves a destination, grants temporary CAS upload access, publishes one staged file in `alvin3y12/codex-downloads`, downloads that public file, verifies its contents, and creates the permanent workspace file. The browser does not send file bytes to an application upload endpoint. No bucket is mounted by this feature.

`server/uploads.ts` exports `initializeUploads(ctx)`, `createUploadRouter(ctx)` and `shutdownUploads(ctx)`. Initialize after the workspace service and before opening the listener. Mount the router at `/api` behind `AuthService.requireSession` and `protectMutations`. Drain uploads before shutting down worktrees. The service uses the existing server-only `downloadBucket` and `downloadToken` configuration; it needs no additional provider settings or credentials in the browser.

## Request flow

| Request | Result |
| --- | --- |
| `GET /api/uploads/status` | Availability, cleanup status and fixed limits. |
| `POST /api/workspaces/:workspaceId/uploads` with `{path,size}` | `201` reserved job with a server-generated UUID and `imports/<uuid>/<filename>` object path. The selected parent folder must exist. |
| `POST /api/uploads/:id/capability` | `200` ephemeral `{accessToken,casUrl,exp}`. Response is `no-store, private`; no token appears in job records. |
| Browser worker uses `@huggingface/hub` `commitIter` | The custom fetch handler obtains the capability from the app and sends bytes only to the allowed HTTPS CAS origins. It intercepts bucket publication instead of calling Hub with a writer credential. |
| `POST /api/uploads/:id/complete` with `{xetHash,sha256}` | `202` job, progressing through `queued`, `publishing`, `importing` and `ready`, or a visible terminal failure. Repeating the same hashes is idempotent; changing either hash is rejected. |
| `GET /api/uploads/:id` | Current durable status; clients poll this after an interrupted finalization response. A ready job includes the created `FileEntry` and its SHA-256 `version`. |
| `DELETE /api/uploads/:id` | Cancels before the final filesystem commit. If the commit has begun, it waits and returns its actual result. It never removes a saved workspace file. |

All job/status responses are `no-store`. A single workspace password grants access to this shared workspace application; upload jobs are not a separate multi-tenant identity system. Every request still requires a valid server-side session, and mutation routes require the existing same-origin protection.

The browser uses a separate worker for each file. That isolates the SDK's module-level token cache and allows cancellation to stop outstanding CAS traffic. The worker computes SHA-256 from the original bounded `File`. Its fixed CAS origin allowlist contains only `https://cas-server-direct.xethub.hf.co` and `https://cas-server.xethub.hf.co`; the server returns the public endpoint described below. The SDK needs WASM hashing/chunking permission in the application CSP; it does not need an external script origin.

The capability route returns the canonical public browser endpoint, `https://cas-server.xethub.hf.co`. On 2026-09-20, the provider-returned `cas-server-direct.xethub.hf.co` resolved to private `10.0.246–249.x` addresses through both the system resolver and Google HTTPS DNS. Chrome refused the resulting local-network request before any bytes were uploaded, even though the provider's CORS preflight allowed the app origin. The server therefore validates the original capability and accepts only the exact known HTTPS CAS URLs (with an optional trailing slash), then maps that single direct alias to the canonical public endpoint. The JWT and expiry remain unchanged. It does not change DNS, introduce a proxy, accept a client-supplied endpoint, grant local-network access or weaken CORS/TLS/CSP.

HF's [Xet authentication specification](https://huggingface.co/docs/xet/auth) names the canonical public CAS endpoint. The SDK carries the CAS URL, token and expiry separately. In a credential-owner live probe on 2026-09-20, the public endpoint returned `401` without a token and `404` for the same absent chunk with the unchanged provider-issued token. The exact built browser worker then completed its deduplication request, received `200` for the xorb and shard uploads, and produced both content hashes. Server publication and anonymous public readback succeeded; all 67 fixture bytes and the SHA-256 matched, and the staged fixture was deleted. Browser TLS, CORS and CSP stayed enabled, without local-network permission, DNS overrides or proxies. No writer token entered the browser and no file bytes passed through the app. This verifies the worker/provider protocol and fixed endpoint normalization; app reservation and persistent workspace installation are separately covered by behavior tests.

## Integrity and filesystem behavior

The server accepts only a relative destination path, an integer size, and the two content hashes. Clients cannot choose another bucket, publication namespace, arbitrary URL, MIME type or overwrite option. Publication uses `application/octet-stream` and a unique server-reserved path. The app never updates a published staging object with different contents. HF buckets themselves are mutable, so this is an application invariant rather than provider object locking.

Before and after downloading the public staging copy, the service checks the remote path, Xet hash, exact byte size and provider `uploadedAt`. It bounds the downloaded body to the reserved size and verifies the actual SHA-256 against the browser's original file. Public resolve redirects are followed manually only to HTTPS HF domains, with no Authorization header or browser credentials. Provider error bodies and signed URLs are never returned in errors or logged by this service.

Workspace installation pins every directory component with Linux `O_NOFOLLOW` directory descriptors. It revalidates the named and pinned folder after persisted commit intent, and copies from an owned, pinned temporary-file descriptor with `COPYFILE_EXCL`. A file created by an editor, terminal or agent while the upload is in progress wins; the upload fails with `FILE_EXISTS`. Symlink parents and final symlinks are rejected, including links that point within the same workspace. The operation participates in worktree file activity and the existing manual-intent/file-changed events.

The native bucket volume does not support hard-link publication. An abrupt process failure during the final native copy can leave an incomplete destination file. Persisted commit intent permits restart recovery to recognize an exact completed file by size and SHA-256. An incomplete, changed or conflicting destination is preserved and reported as interrupted; the service never replays an overwrite. Owned temporary files are removed safely during normal completion and startup recovery.

## Persistence, expiry and resource limits

Ordinary durable state is saved through `ctx.store` as `upload-jobs-v1.json` under the native `/data` state directory. It contains paths, hashes, timing, state and bounded capability issuance timestamps. Neither the main HF writer token nor temporary capability tokens are persisted there. Completed workspace files are ordinary persistent files, independent of staging cleanup and logout.

Published staging copies expire 24 hours after the provider's actual `uploadedAt`, not the browser's timestamp or a file's old modification time. Cleanup runs before startup readiness, periodically while the process runs, and at the nearest known expiry. Startup catches expiries missed while a Space was stopped. A canceled or failed staged transfer is eligible for earlier cleanup. A ready upload remains ready after its staging copy is removed.

Cleanup only lists `imports` and only deletes well-formed `imports/<uuid>/<filename>` files in the fixed transfer bucket. It includes orphan objects left by a crash after publication but before persistence. A full bounded scan completes before deletion begins; objects are reread before deletion to avoid removing a replacement based on stale listing data. Already missing objects are treated idempotently, including removals by the existing download cleanup. Unknown timestamps or partial deletion failures keep the service visibly unavailable and cause a scheduled retry. No upload cleanup operation touches workspace files, the main data bucket, or the `exports` download namespace.

Default limits are 25 MiB per file, eight active sessions, two concurrent server imports, 30 minutes per browser reservation, ten minutes per server transfer/import, four capability requests per reservation, and 32 capability issuances per 20-minute window. Issuance timestamps survive restart. The service retains at most 2,000 job records, restricts metadata and response bodies, and never accepts an unbounded queue. Active reservations are preserved across restart until expiry; interrupted finalizations fail visibly unless their completed filesystem commit can be verified.

## Provider permission boundary

The main HF writer token is used only by the server for the fixed bucket's token, metadata, publication and deletion routes. The browser receives a provider-issued short-lived Xet CAS JWT. Observed provider TTL is 15 minutes; the server rejects unexpectedly long, malformed or nearly expired capabilities, and validates the exact CAS origins. Canceling or logging out cannot revoke a JWT already issued by HF, but the app stops accepting publication for a canceled or expired reservation.

HF's documented Xet write-token route accepts the bucket namespace and name. It has no documented key, byte-size or custom-expiry attenuation parameters. Therefore the temporary CAS capability itself is **not** constrained to the reserved file or byte count. Namespace, destination, size, concurrency and content checks apply at the app's publication/import boundary. Unpublished CAS blocks are managed by HF; the application has no supported per-block removal API. The 24-hour cleanup policy concerns published bucket staging copies, not provider-internal unreferenced CAS blocks.

The supported protocol is documented in the [HF Hub OpenAPI specification](https://huggingface.co/.well-known/openapi.json), the [official JavaScript Xet write-token implementation](https://github.com/huggingface/huggingface.js/blob/main/packages/hub/src/utils/xetWriteToken.ts), and the [official bucket commit implementation](https://github.com/huggingface/huggingface.js/blob/main/packages/hub/src/lib/commit.ts). The installed browser SDK is pinned to `@huggingface/hub` 2.17.3. The [HF bucket documentation](https://huggingface.co/docs/hub/storage-buckets) describes buckets as mutable, non-versioned storage.

The unit suite uses actual temporary workspace files and the ordinary JSON store, replacing only the external HF boundary. It checks binary and empty-file import, hashes and sizes, no-follow path races, create-only conflicts, cancellation/commit races, shutdown draining, restart recovery, capability containment, authenticated HTTP routes, orphan discovery and scheduled/startup expiry. A real-browser/live-provider probe remains separate and must use the deployment coordinator's bounded fixture reservation; no test or implementation reads deployment credential files.
