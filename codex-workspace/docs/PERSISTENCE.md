# Persistence on the public Hugging Face bucket

Both the Space and `alvin3y12/data` remain public, as requested. Workspace files, Git repositories, terminal home files, conversation history, and ordinary app metadata are stored as readable files in the bucket. The application does not encrypt or create an encrypted copy of these files. The workspace password protects access to the running application; it does not restrict downloads from the public bucket.

## Platform configuration

Attach `alvin3y12/data` to the Space at `/data` with **read-write** access in the Space's **Settings → Storage / attached volumes** controls. Set `DATA_DIR=/data`. Hugging Face provides the mount before starting the app. The app must never invoke mount utilities, `hf-mount`, FUSE, NFS setup, `proot`, a Docker daemon, or any container/sandbox machinery. Hugging Face documents bucket attachments as managed runtime volumes and recommends them for persistence across Space restarts. [Spaces storage](https://huggingface.co/docs/hub/spaces-storage), [bucket access patterns](https://huggingface.co/docs/hub/storage-buckets-access#volume-mounts-in-jobs-and-spaces).

Set `WORKSPACE_PASSWORD`, `SESSION_SECRET`, and `ENCRYPTION_KEY` in Space **Secrets**, outside the public repository and bucket. Keep the deployment token outside public files as well. GitHub and model API credentials are separate from workspace files: the app's credential store protects those values; workspace contents remain plaintext. A deployment token is not needed by ordinary app storage operations after the platform attaches the bucket.

## Data layout and lifetime

| Location | Contents | Restart behavior |
| --- | --- | --- |
| `DATA_DIR/workspaces/` | Working trees, hidden `.git` directories, retained workspace files, trash | Read from the same attached bucket after restart |
| `DATA_DIR/home/` | Terminal home and persistent user tool configuration | Read from the same attached bucket after restart |
| `DATA_DIR/codex-workspace/state/` | Workspace registrations, settings, threads, review state, account metadata, protected credentials, file metadata | Loaded by the server after restart |
| `/tmp` | Build output, bounded temporary work, process-local transient state | May disappear when the Space stops or restarts |

Files intentionally written outside `DATA_DIR` by a terminal command are outside the app's persistence contract. Running terminal processes and in-flight model requests cannot survive replacement of the Space instance. Durable thread and workspace files are separate from those live processes.

Buckets are mutable object storage without Git-style version history. Deleting or overwriting a bucket object does not create a recoverable historical version. Review snapshots and workspace trash are application files and must be retained under the bucket if they are to survive restart. [Storage Buckets](https://huggingface.co/docs/hub/storage-buckets#buckets-vs-repositories).

## Filesystem semantics

The managed bucket volume is a network-backed filesystem. Treat one running Space instance as its writer. In-process JSON updates must be serialized, and writes must use a temporary file followed by rename so a failed write cannot replace valid state with a partial JSON document. A missing state file may use a default; malformed existing JSON must report an error.

Hugging Face's filesystem implementation documents eventual remote consistency, asynchronous uploads in advanced-write mode, and no cross-client locking. POSIX permission changes, timestamps, and symlinks can be represented while a mount is alive but are not all retained as remote object metadata. Local `close()` or rename completion alone therefore does not prove that an abrupt instance loss will preserve the latest bytes. Git history retains its own tracked executable/symlink metadata, but that is distinct from metadata on an uncommitted working tree. These are upstream limitations to verify against the actual managed volume, not reasons for the app to mount a second filesystem. [Hugging Face filesystem consistency](https://github.com/huggingface/hf-mount#consistency-model), [filesystem features](https://github.com/huggingface/hf-mount#features).

The current upstream advanced-write `fsync` implementation queues a background upload and returns immediately. Calling `fsync` is not a substitute for checking that the bucket has received the data. [Upstream filesystem implementation](https://github.com/huggingface/hf-mount/blob/main/src/virtual_fs/mod.rs).

## Restoring working-project metadata

`server/file-metadata.ts` compensates for lost filesystem metadata with the readable `filesystem-metadata.json` state file. It records symlink targets and the observed permission mode of every regular file and directory, including ordinary `0644` files and `0755` directories. Native bucket defaults after a fresh instance can differ from these modes, so omission is not evidence of a durable default. Coverage includes hidden Git paths, dependency command links such as `node_modules/.bin`, home configuration, workspace trash, empty folders, and the two configured roots. Ordinary file contents remain in their original files; this mechanism does not encrypt or duplicate them.

The version-1 manifest has an optional, directory-only `restoreMissing` field. New empty-directory records set it to `true`; new nonempty-directory records set it to `false` and preserve modes only when the path exists. A mode-only record does not authorize creating a missing folder or a replacement tree for missing file bytes. Explicit saved links and restorable empty folders can still create their necessary parent directories, subject to workspace deletion exclusions and missing-workspace protection. Unreadable directories retain their previous restoration intent; a newly encountered unreadable directory receives no recreation authority.

Legacy directory records without this field keep their previous recreation behavior. Older sparse manifests remain readable, but unlisted legacy paths have no historical mode evidence: startup does not infer `0644` or `0755`, sweep them with `chmod`, or rewrite their modes. A later complete capture records their currently observed modes for future restarts; it cannot recover permissions already lost before that capture. The manager covers only the configured workspace and home roots. Unix modes of internal state JSON outside those roots are not part of this restoration contract.

Before the app accepts work, `initialize()` validates the entire saved manifest, restores missing links and directories whose records permit recreation, and applies saved modes to existing regular files and directories. The application defers the fresh metadata scan until background capture starts; a slow refresh cannot abort startup after successful restoration. Invalid manifests, missing tracked roots and restoration failures still prevent startup. Existing regular files and changed symlinks win over conflicting saved links. Missing regular-file contents are never fabricated. Traversal is anchored to open directory descriptors, checks paths stay in the expected directory, and never follows a symlink ancestor. Links pointing outside a workspace may be preserved as user files; workspace APIs continue to enforce their own access boundary.

Only initialization restores metadata. Later captures observe deletions and renames, so deleting a link during a running session never causes it to be recreated by a background capture. Workspace changes and terminal exit trigger debounced capture; a 20-second scan also detects direct terminal changes. Shutdown stops terminal processes before a final capture. Overlapping requests are serialized, including a change arriving while the previous manifest is being saved, and unchanged metadata does not trigger another bucket write.

The scan is bounded to 250,000 filesystem entries and 128 path components, with bounded concurrent stat calls. The manager defaults to a 90-second traversal budget; the application allows five minutes for the slow native bucket. An I/O failure or exceeded budget retains the previous complete manifest, reports an error and permits a later background retry. No partial scan replaces saved metadata. Explicit captures used by file operations and shutdown still wait for successful completion and reject failures. For an unreadable directory, known metadata below that directory is retained rather than treated as deleted. The manager reports conflicts and capture failures through its status and events. Sockets, FIFOs, device nodes, and running processes are transient and have no bucket representation. Native upload latency and the platform's shutdown deadline still apply to both ordinary files and this metadata file.

## Verification boundaries

`tests/storage.test.ts` exercises storage correctness against a local filesystem, including reopening durable state, concurrent updates, traversal rejection, and preservation of valid state after an invalid write. `tests/file-metadata.test.ts` uses a fresh Node process and actual temporary files to restore captured `0644`/`0755` modes after changing those exact fixture paths to `0666`/`0777`. It verifies file bytes, custom modes, links and empty folders while leaving unlisted paths and excluded generations untouched. It also covers legacy sparse records, missing nonempty directories, unreadable subtrees, stale directory descriptors, malformed manifests, deletion/rename capture, failed saves, and changes arriving during a save. Passing these tests does not establish that a Space has a native bucket attached or that uploads have reached Hugging Face.

The deployment check must separately inspect the Space's attached-volume configuration, write a distinctive ordinary file and app record, confirm the file appears in `alvin3y12/data`, restart the Space through Hugging Face, and then read both through the app. Do this with a dedicated verification workspace. Record the checked Space revision and outcome in deployment evidence; leave native-bucket restart durability unverified until that check succeeds. Do not infer a mount from the existence of an ordinary `/data` directory.
