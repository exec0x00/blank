# Module contract

API endpoints below start `/api`. Success JSON is returned directly; failures are `{ error: string, code?: string }`. Server sessions authenticate every API route except session status/login; browser mutations require same-origin headers. Session-bound event streams close on logout/expiry and enforce bounded output/backpressure.

Public `GET /` always returns the exact plain-text body `status: ok`, regardless of session or query parameters. It never redirects or loads the application. `/work` and `/work/` serve the workspace login/application shell, and focused agent/editor links keep their `workspace`, `thread` and `view` query parameters there. `/health` remains the public JSON health endpoint; API, WebSocket and asset paths are unchanged.

The official Codex CLI is the only agent runtime. Node translates authenticated requests to its app-server over private stdio. It does not send model requests, schedule agent turns, implement tools, or reconstruct native history from local rollout files. See [CLI_CAPABILITY_AUDIT.md](CLI_CAPABILITY_AUDIT.md) and [CLI_RUNTIME_POLICY.md](CLI_RUNTIME_POLICY.md). This document describes source contracts; release evidence belongs in [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md).

## Core and native preferences

- `GET /session` → `{ authenticated }`; `POST /session { password }`; `DELETE /session`.
- `GET /bootstrap` → Bootstrap with the first bounded workspace/account pages, exact selected workspace, settings and interface preferences. Account connections and repository selections persist across logout/restart.
- `GET /settings` → AppSettings. `PATCH /settings` accepts `model`, `reasoningEffort`, `reasoningSummary` (`auto|concise|detailed|none` or null), `verbosity` (`low|medium|high` or null), `autoApprove`, `webSearchMode` (`disabled|cached|live`), `fastMode`, `serviceTier`, `maxConcurrentAgents`, `modelContextWindow`, `autoCompactTokenLimit`, `fontSize` (10–24), and `wordWrap`. Fast defaults on; null context/compaction overrides restore model-aware automatic values. Dark appearance is fixed.
- `GET /settings/native` → `CodexNativeSettings`: effective and user configuration, writable layer version, official schema/provenance, editable/managed keys, native model capacities, private MCP variable names and restart status. Private credential values never appear in this response.
- `PATCH /settings/native { expectedVersion, edits:[{keyPath,value}], preferences?, mcpEnvironment?:[{name,value}] }` validates structured edits and host constraints, performs a native version-checked batch write, and returns a refreshed snapshot. Null removes an override or private variable. MCP private values use encrypted storage and native environment references. No caller-selected configuration path or arbitrary RPC is accepted.
- `POST /settings/native/mcp/check` explicitly reads native MCP connection/tool status in bounded pages. Saving private variables may require restarting the idle native process before they are available to configured servers.
- Agent preferences use native `config/read` and version-checked `config/batchWrite`; native effective values are authoritative. Null removes a supported nullable override. Higher-priority native overrides and uncertain write acknowledgments are reported honestly; writes are never automatically replayed. Editor preferences remain available while the CLI installs.
- Startup may import actually saved, supported web preferences only when no native user/effective choice already exists. Reading settings does not initialize preferences or make model requests.
- `GET /models` → `{ backend:'codex-cli', catalog:CodexModel[], models:string[], connected:boolean }` from the installed CLI's `model/list`. Each catalog row separates native `id` from literal wire `model`, supported effort values and the native default. No upstream `/models` request occurs. The requested Daybreak Red native row remains selectable even when hidden by the default picker; Cyber and other explicit literal IDs can be selected without fabricated catalog metadata or capacities. Native provider fallback is disabled and real service rejection stays visible. Custom profile/probe endpoints and arbitrary output-token controls were removed.
- `GET /provider/status` exposes managed native-runtime readiness only. No provider/login/key/endpoint editing routes exist.
- `GET /codex/runtime` → CodexRuntimeStatus: actual running/installed versions, installation/update state, error, active count and supported capabilities.
- `POST /codex/runtime/update {}` → 202 status. The server installs/verifies latest official Codex asynchronously; Settings polls status. Switching requires native work, approvals, queues, goals and background terminals to be idle. A failed installation preserves the previous running release. Updates never replace native history/configuration.
- `POST /codex/runtime/restart {}` → 202 status. Restart the verified installed release without reinstalling it, subject to the same idle-work checks. Native history and user configuration remain persistent.

See [WORKSPACE_SETTINGS.md](WORKSPACE_SETTINGS.md) for model-aware context limits, configuration controls, inline output and focused agent/editor windows.

## Interface preferences

- `GET /ui-state` -> UiState. `PATCH /ui-state { revision, changes, migration? }` -> UiState uses the existing per-field revision journal. Each request accepts 1–512 unique field changes and at most 512 KiB; malformed selections return `400 VALIDATION_ERROR`, oversize requests `413 UI_STATE_TOO_LARGE`, conflicting newer values `409 UI_STATE_CONFLICT`, and invalid saved state `503 UI_STATE_INVALID`.
- Workspace UI preferences also accept `{ section:"workspace", workspaceId, key:"serviceTier", threadId: nativeThreadId|null, value: tier }`. These bounded composer choices use independent per-conversation revisions in the saved journal; changing one does not write global native configuration or overwrite another conversation's choice. `threadId:null` selects the separate unsent-draft choice. Saved values appear in `workspaces[workspaceId].serviceTiers`, keyed by thread ID or `draft`.
- Pane changes use `{ section:'layout', profile:'desktop'|'laptop'|'tablet'|'mobile', key:'agentWidthRatio', value }` with a finite ratio 0.1–0.85, or `key:'explorerWidth'` with an integer 160–720 CSS pixels. Preferences are per layout profile across workspaces. Rendering clamps to available room without overwriting desired saved sizes; only a completed drag or keyboard resize persists a change. Existing view/editor/workspace selection fields retain their contracts. See [PANE_RESIZING.md](PANE_RESIZING.md).

## Workspace module
- `GET /workspaces` -> Workspace[]; `POST /workspaces { name, initializeGit?: boolean }` -> Workspace.
- `GET /workspaces?limit=&cursor=&query=&refresh=` -> WorkspacePage `{ workspaces:Workspace[], nextCursor:string|null, previousCursor:string|null, offset, total?, revision?, selected?:Workspace }`. Supplying any of these page options selects the page response; the bare route retains its legacy array. Browser requests use explicit paging. Limit defaults to 40 and is at most 100. Query is a trimmed, case-insensitive substring of workspace name/path, at most 200 readable characters. Opaque cursors bind the query, limit and revision; a changed list returns `409 WORKSPACE_LIST_CHANGED`, while malformed or mismatched cursors return `400 INVALID_WORKSPACE_CURSOR`. Unknown or repeated options return `400 INVALID_WORKSPACE_PAGE`.
- `refresh=1|true` forces a metadata refresh before producing the bounded page; concurrent refreshes share one registry read. `refresh=0|false` does not force refresh. To restart after a list revision changes, request the first page without the old cursor. Visible workspace rows and the exact selected workspace are checked against canonical records.
- `GET /workspaces/:id` -> the exact live Workspace, including an active workspace outside the loaded page. Archived, absent or verified-missing workspaces return 404; other failures remain visible. Never infer deletion from absence in a partial workspace page. Use the exact route to confirm a selected workspace and preserve its local state until that check resolves.
- `PATCH /workspaces/:id { name?, githubAccountId?, active?: boolean }` -> Workspace.
- `GET /workspaces/:id/deletion` -> WorkspaceDeletionPlan (`{ workspaceId, mode:'trash'|'permanent', retentionDays:30|null }`). Verified GitHub-backed workspaces use permanent local deletion; mutable account selection alone does not establish repository provenance.
- `DELETE /workspaces/:id { expectedMode:'trash'|'permanent' }` -> WorkspaceDeleteResult: `{ removed:true, mode:'trash', trash }` for an ordinary workspace, or `{ removed:true, mode:'permanent', workspaceId }` after a GitHub-backed workspace's local files are purged. A changed classification fails with 409 before mutation; permanent deletion requires an explicit matching mode. Managed checkouts use their guarded Worktrees lifecycle instead.
- `GET /workspace-trash` -> WorkspaceTrashEntry[]; `POST /workspace-trash/:id/restore {}` -> Workspace, without overwriting a new destination; `DELETE /workspace-trash/:id` -> `{ deleted:true, id }` permanently removes that trash entry.
- Missing workspace roots are reconciled only after a verified absence. They leave the active list with `reason:'missing'`, `state:'missing'` and `canRestore:false` if files are gone. Permission errors, unsafe links and transient storage failures must not be treated as deletion. Recovery issues remain visible; registration/account associations survive recoverable moves.
- Workspace trash entries expose `expiresAt`, exactly 30 days after `deletedAt`. Startup and scheduled cleanup permanently purge expired entries, retaining visible failures for safe retry. Permanent GitHub deletion may use an internal recovery journal during the operation but never offers a restorable trash entry.
- `GET /workspace-deletions` -> WorkspaceDeletionStatus[] for unfinished permanent deletions. `POST /workspace-deletions/:id/retry {}` retries that exact deletion journal and returns the permanent WorkspaceDeleteResult; it cannot start a fresh deletion of a newer workspace generation. These statuses have no restore action.
- Permanent removal and expired-trash purge now invoke the wired workspace-artifact lifecycle after project/file-trash payload removal. The internal, generation-bound request rechecks `assertCurrent()` between rewind backups, conversation/context/memory state, generic attachments, uploaded images, generated originals and Git checkpoints. Ordinary restorable trash/restore retains those artifacts. Missing cleanup support returns `503 WORKSPACE_ARTIFACT_CLEANUP_UNAVAILABLE`, superseded ownership `409 WORKSPACE_ARTIFACT_CLEANUP_CHANGED`, and incomplete cleanup `409 WORKSPACE_ARTIFACT_CLEANUP_FAILED`; retained journals support the exact existing retry. Account credentials, reusable settings and unrelated workspaces are outside this cleanup.
- `GET /workspaces/:id/tree?path=` -> FileEntry[].
- `GET /workspaces/:id/tree-page?path=&limit=&cursor=&snapshot=` -> DirectoryPage `{ path, entries:FileEntry[], nextCursor:string|null, snapshot, order:'filesystem', unchanged?:true }`. Path defaults to the workspace root; limit defaults to 100 and is at most 200. A continuation cursor is bound to the same workspace, path and limit. Pages follow the native directory stream, with folders first and natural name ordering within each page; there is no global alphabetical ordering guarantee.
- A first-page tree request may send its previous `snapshot`, without `cursor`. An `unchanged:true` response carries placeholder `entries:[]` and `nextCursor:null`; preserve all loaded pages and their existing continuation cursor. `409 DIRECTORY_PAGE_STALE` requires a fresh first-page request. Listing entries need not include size or modification time.
- `GET /workspaces/:id/tree-entry?path=` -> FileEntry for one complete workspace-relative path, including any parent folders. It checks that exact entry without walking preceding pages, rejects symlink ancestors, and reports a final symlink through `isSymlink` without following it.
- `GET /workspaces/:id/file?path=` -> FileContent.
- `PUT /workspaces/:id/file { path, content, expectedVersion? }` -> FileContent; 409 on conflict.
- `POST /workspaces/:id/files { path, kind: 'file'|'directory' }` -> FileEntry.
- `POST /workspaces/:id/rename { path, newPath }`.
- `DELETE /workspaces/:id/file?path=` (move to persistent trash).
- `GET /workspaces/:id/search?q=&caseSensitive=&regex=&include=` -> SearchMatch[].
- `POST /workspaces/:id/replace { query, replacement, paths?, caseSensitive? }` -> `{ files, replacements }`.
- `GET /workspaces/:id/file-paths?q=` -> string[] for fuzzy quick open; `GET /workspaces/:id/trash` lists recoverable items; `POST /workspaces/:id/restore { trashId }` restores without overwriting.
- `GET /workspaces/:id/trash/page?limit=&cursor=&q=` -> FileTrashPage `{ items, previousCursor, nextCursor, hasMore, scanned, unavailable, order:'filesystem' }`. Default limit 25, maximum 50; `q` is optional and at most 160 characters. Each call examines at most 100 native entries and respects a 256 KiB metadata output budget, so a sparse or empty page may still have a next page. There is no global date-sort or total-count claim. Cursors bind workspace, query and limit; a changed directory returns `409 FILE_TRASH_CURSOR_STALE`, a restarted/evicted/idle-expired stream returns `409 FILE_TRASH_CURSOR_EXPIRED`, and invalid bindings return `400 INVALID_FILE_TRASH_CURSOR`. Use First page recovery when an old cursor is no longer available. At most eight context-owned sessions and eight replay pages per session are retained, within a 4 MiB total cache and two-minute idle expiry. Restore resolves the exact trash ID independently of list position.
- File trash entries include `expiresAt` and retain their original 30-day deadline when a whole workspace is trashed or restored. `GET /workspaces/:id/trash-status` -> `{ issue:string|null }` reports bounded cleanup warnings while healthy entries remain available. Expired entries cannot be restored.
- `GET /workspaces/:id/download?path=` file download.
- `PUT /workspaces/:id/upload?path=` raw bytes, bounded.

`WorkspaceService` is constructed with `(config:AppConfig, store:JsonStore, options?:WorkspaceLifecycleOptions)`. Its async list/get/create/path operations retain their existing signatures; lifecycle options supply metadata capture, signed deletion preflight and exact-generation artifact cleanup from the coordinator.

Startup loads signed metadata exclusions and reconstructs file-rewind admission barriers before workspace/job recovery or agent activation. Workspace and managed-worktree cleanup keep their exact removal-generation authority; ordinary recovery/status reads do not authorize a fresh destructive operation or replay an uncertain file rewind. `server/workspace-artifacts.ts` composes cleanup, and `server/index.ts` wires initialization, authenticated routes and shutdown. This is source wiring, with current lifecycle verification still pending.

## Operational list pages

- `GET /workspace-trash/page?offset=&limit=&q=` -> WorkspaceTrashPage with WorkspaceTrashEntry items.
- `GET /workspace-deletions/page?offset=&limit=&q=` -> WorkspaceDeletionPage with WorkspaceDeletionStatus items.
- `GET /workspaces/:id/worktrees/page?offset=&limit=&q=&sourceWorkspaceId=` -> ManagedWorktreePage for that repository family, adding exact retained `repository:Workspace` and at most three active `sources:Workspace[]` to the common page fields. The optional source workspace is validated against exact active registrations in the same family; sources do not depend on the first workspace-list page.
- `GET /workspaces/:id/file-transfers/page?offset=&limit=&q=` -> FileTransferPage with FileTransferStatus items.

These pages share `{ items, offset, limit, total, hasMore }`. Offset defaults to zero and is at most 10,000; limit defaults to 25 and is at most 50. The optional `q` is a trimmed, case-insensitive filter of at most 160 readable characters. Arrays, control characters and unknown query options return `400 INVALID_OPERATIONAL_PAGE`. Use the returned offset because removing the last row can move a request to the nearest existing page.

Trash and permanent-deletion search match workspace name/ID; worktree search matches current name, path and branch; file-transfer search matches source, destination and kind. Trash/deletion pages show newest deletions first, transfers newest creations first, and worktrees oldest creations first. Bounded journal discovery validates records beyond the visible page, while native content/Git status checks are limited to the selected page. Malformed records remain visible errors; a selected entry that disappears during loading returns `409 OPERATIONAL_LIST_CHANGED`.

Compact discovery metadata is capped at 10,000 identity/order pairs and 2 MiB, with at most four simultaneous scans (`429 OPERATIONAL_LIST_BUSY`). Discovery-limit failures remain explicit; there is no cross-request operational metadata cache or background replay.

The complete array and internal cleanup APIs retain their existing behavior. Loading or refreshing these pages never replays a deletion, transfer or other destructive action; mutations remain explicit requests against their exact saved identities.

## Paged workspace files

- `GET /workspaces/:id/file-info?path=` -> WorkspaceFileInfo `{ path, size, version, language, paged, maxPageBytes, editable, readOnlyReason, totalLines }`. This is metadata, not a claim that all source bytes have been read or validated. Files above 5 MiB use paged editing; files above 64 MiB remain readable in pages with `editable:false`.
- `GET /workspaces/:id/file-page?path=&version=&offset=&cursor=` -> WorkspaceFilePage. A fresh request may omit version and defaults to byte offset zero. Returned cursors pin the source identity and byte offset; continue with the cursor rather than changing its offset. Pages target 128 KiB of UTF-8 text and keep complete character boundaries, with bounded line-boundary alignment. The response includes `content`, `byteStart`, exclusive `byteEnd`, nullable `startLine`/`endLine`, `startsMidLine`, `endsMidLine`, `pageToken`, `nextCursor:string|null`, and `previousOffset:number|null` alongside file metadata.
- `POST /workspaces/:id/file-search { path, version, query, caseSensitive?, cursor? }` -> WorkspaceFileSearchResult. Search is literal, case-sensitive by default, and query text is at most 4,096 UTF-8 bytes. Each request scans at most 2 MiB and returns at most 100 matches, including overlapping matches, with byte ranges, line numbers and bounded previews. Continue the same query using `nextCursor`; `searchedFrom`, `scannedThrough`, `complete` and nullable `totalLines` describe actual progress. Stopping continuation stops the search.
- `PUT /workspaces/:id/file-range { path, pageToken, content }` -> WorkspaceFilePage for the exact submitted replacement range, with a new version and token. The submitted UTF-8 content may be at most 256 KiB; both the entire source file and resulting file must be at most 64 MiB. The signed token binds the workspace/path, canonical target, native identity, original byte range and range digest. A save checks that identity and the original bytes before replacement; a stale edit returns `409 VERSION_CONFLICT`.
- `GET /workspaces/:id/file-recoveries` -> WorkspaceFileRecovery[] `{ id, workspaceId, path, recoveryPath, completeCopy, state:'running'|'retained', phase, createdAt, issue }`. This endpoint only inspects saved recovery metadata. It does not replay edits, overwrite current files or remove retained copies; `completeCopy` distinguishes a full edited copy from an interrupted preparation.

File-page versions identify the native source and differ from the legacy small-file content digest. Do not pass them as `expectedVersion` to the legacy file save or public-download request. Line counts remain unknown until a contiguous scan reaches EOF. Invalid UTF-8 or binary content returns `415 BINARY_FILE`; an oversized replacement returns `413 FILE_PAGE_TOO_LARGE`, and a source/result above the save cap returns `413 FILE_RANGE_SAVE_LIMIT`.

Range saves prepare a separate edited recovery copy and keep it when confirmation fails. Busy/resource admission returns `429 FILE_SAVE_BUSY` or `503 FILE_SAVE_RESOURCES`. `503 FILE_SAVE_CONFIRMATION_PENDING` means replacement was attempted but could not be confirmed; clients must retain their edits and inspect the current file and recovery copy before retrying. Startup recovery does not automatically replay a save or remove retained copies. These contracts describe source behavior; native persistence and race verification remain separate release checks.

## Public-bucket transfers

All control routes require the workspace session and the usual same-origin mutation protection. The separate public `alvin3y12/codex-downloads` bucket is accessed through its API and is never mounted. Temporary published copies expire after 24 hours, with startup and scheduled cleanup; imported workspace files remain persistent.

- `GET /downloads/status` -> DownloadServiceStatus; `POST /workspaces/:workspaceId/downloads { path, expectedVersion? }` -> DownloadJob (202).
- `GET /downloads/:id` -> DownloadJob; `GET /downloads/:id/events` streams job progress; `DELETE /downloads/:id` cancels preparation. Ready jobs expose direct public URLs for immutable snapshots. Production browser downloads use this workflow instead of streaming file bytes through the app server.
- `GET /uploads/status` -> UploadServiceStatus with readiness and limits.
- `POST /workspaces/:workspaceId/uploads { path, size }` -> UploadJob (201). The destination is create-only, its parent must exist, and each file is at most 25 MiB. The server chooses the unique public staging object path.
- `POST /uploads/:id/capability {}` -> UploadCapability (`accessToken`, `casUrl`, `exp`), returned only in an authenticated, non-cacheable response. This is an expiring provider CAS upload capability, never the main bucket writer token. After validating the exact provider response, the server selects the canonical public CAS endpoint when Hugging Face returns its internal direct alias, without changing the token or expiry. The browser transfers file bytes directly to Hugging Face in an isolated worker.
- `POST /uploads/:id/complete { xetHash, sha256 }` -> UploadJob (202). The server validates the reserved hash and size, publishes the staging object, downloads its bytes from the fixed public bucket, verifies SHA-256 and installs the file without overwriting an existing destination.
- `GET /uploads/:id` -> UploadJob; `DELETE /uploads/:id` requests cancellation. A job reaches `ready` only after the workspace import is committed. Cancellation and failed-response reconciliation must report a completed import honestly.

The provider's temporary CAS capability is scoped to the bucket, not one filename. The app controls published paths and import limits; it cannot independently revoke an already issued provider capability or delete unpublished CAS blocks. Published staging copies and their cleanup remain under the app's control.

### Conversation file attachments

General file attachments are immutable originals separate from editable workspace files and image attachments. A `FileAttachmentReference` is `{ id, sha256 }`; submitted references must belong to the selected workspace. Public `FileAttachment` metadata adds `workspaceId`, `name`, `mimeType`, `bytes` and `createdAt`, without original bytes, storage paths or credentials. Each file is at most 25 MiB; one message accepts at most eight files and 50 MiB in total. Unsubmitted drafts expire after 24 hours; submitted originals remain durable.

- `GET /file-attachment-uploads/status` -> FileAttachmentUploadStatus with readiness and limits.
- `POST /workspaces/:workspaceId/file-attachments/uploads { name, size, mimeType? }` -> FileAttachmentUploadJob (201). The filename is a single name, not a destination path. The server reserves a unique public staging object.
- `POST /file-attachment-uploads/:id/capability {}` -> UploadCapability in an authenticated, non-cacheable response. The browser uploads directly to the provider CAS service, using the temporary capability rather than a bucket writer credential.
- `POST /file-attachment-uploads/:id/complete { xetHash, sha256 }` -> FileAttachmentUploadJob (202). The server publishes staging, downloads the original, validates its size and SHA-256, and commits the immutable attachment. Published staging expires after 24 hours with startup and scheduled cleanup.
- `GET /file-attachment-uploads/:id` -> FileAttachmentUploadJob; `DELETE /file-attachment-uploads/:id` requests cancellation. A ready job exposes its `attachment` metadata for submission.
- `GET /workspaces/:workspaceId/file-attachments/:attachmentId/inspect?sha256=&offset=&maxBytes=` -> FileAttachmentInspection. Offset is in bytes and defaults to zero; `maxBytes` defaults to 16 KiB and is at most 64 KiB. UTF-8 previews preserve complete characters and return `content`; binary previews return at most 4 KiB as `hex`, with an explanatory notice. The response includes the actual offset, bytes read, total size, truncation and an optional continuation offset. Inspection does not execute files or extract PDF/archive contents.
- `POST /workspaces/:workspaceId/file-attachments/:attachmentId/downloads { sha256 }` -> DownloadJob (202). Use the normal `/downloads/:id` and event routes to obtain the immutable public link. There is no raw binary attachment download route. Keep a clickable Download file action when browser fetch is blocked, and report “Download requested” without claiming the browser saved it.
- `DELETE /workspaces/:workspaceId/file-attachments/:attachmentId?sha256=` discards an eligible unsubmitted draft. Submitted originals remain retained for conversation history.

### Photo attachment staging

The photo picker uses the same direct browser CAS upload and public staging lifecycle as general files. After the generic upload reaches `ready`, `POST /workspaces/:id/attachments/from-upload { uploadId,sha256,detail? }` returns the existing `ImageAttachment` metadata. `detail` is `high|original`; the existing 8 MiB input and raster/container/dimension limits still apply; accepted image bytes are preserved. The app receives JSON references, not the photo body. The route accepts only an exact ready upload owned by that workspace and reads its pinned verified source before image publication.

Promotion identity binds workspace, upload, original SHA-256 and detail. Retries verify the saved image bytes and return the same retained reference; an explicitly discarded promotion cannot silently reappear. The client keeps the verified promotion receipt before best-effort disposal of the unused generic draft. Its public staging copy retains the original 24-hour cleanup schedule. Uncertain publication remains visible and never causes an implicit message submission. Existing from-workspace image references and the legacy raw HTTP route remain compatible; the browser photo picker uses staged promotion.

### Generated images

The agent's native `generate_image` function calls a separate hosted-image Responses helper through the same fixed endpoint and immutable accepted model/options. It accepts a prompt of at most 16,384 characters / 32 KiB and at most five existing workspace image paths or one-to-five recent context images, using `referenced_image_paths` or `num_last_images_to_include` exclusively. Generation is unavailable in Plan/review modes. The helper has a 120-second deadline and output budget capped at 4,096 tokens, retains required host instructions and owning-run usage/budget checks, and never retries with a different model. There is no unauthenticated or standalone HTTP generation route.

- `GET /workspaces/:workspaceId/generated-images/:id/content?sha256=` returns the verified original PNG/JPEG/WebP as an authenticated, no-store preview. IDs use `img_` plus 64 lowercase hexadecimal characters and require the paired 64-hex SHA-256. Immutable originals and manual delivery are bounded to 8 MiB; public metadata carries dimensions, byte count, provenance IDs and `previewUrl`, never base64 or storage paths.
- `POST /workspaces/:workspaceId/generated-images/:id/save { sha256, path, threadId? }` -> GeneratedImageSave `{ image, path, entry, version }` (201). This creates a new file in an existing workspace folder, preserving the original and refusing overwrite/symlink traversal. Optional `threadId` asserts original asset ownership; it does not turn a manual save into an agent change. Existing destinations return `409 FILE_EXISTS`.
- `POST /workspaces/:workspaceId/generated-images/:id/download { sha256 }` -> DownloadJob (202), using the existing immutable public-bucket preparation/status/events flow. Temporary published downloads expire after 24 hours; the generated original has no download-expiry deadline. Retain the clickable public fallback and honest “Download requested” status.
- Native `list_generated_images` and `read_generated_image` resolve only exact delivered generation cards, including retained cards in explicit forks. `copy_generated_image { id, sha256, path }` uses normal mutation permission and bounded binary review, with a **2 MiB** agent-copy cap (`413 GENERATED_IMAGE_REVIEW_LIMIT`). Larger originals remain available to manual Save/Download. Its result explicitly reports whether saved review/Undo is available; guessed IDs, pending rows, copied text and delegated parent history grant no image access.

The transport commits verified final bytes once; saved history keeps pinned references and rehydrates exact bytes only for request-local model replay. Public activity preserves readable progress and a real committed image even if its response later stops. Startup/Stop do not speculate that an interrupted or possibly billed generation should be repeated. Preview/delivery routers, engine dispatch, cards and artifact cleanup are wired in source; historical PNG/35-case asset evidence does not verify this newer complete flow. See [MULTIMODAL_PARITY_PLAN.md](MULTIMODAL_PARITY_PLAN.md).

## Managed worktrees

- `GET /workspaces/:id/worktrees` -> ManagedWorktree[] for the repository family.
- `POST /workspaces/:id/worktrees { name?, branch?, createBranch?, base? }` -> `{ workspace, worktree }` (201). Omit branch for a detached checkout.
- `POST /workspaces/:id/worktrees/:worktreeId/open {}` -> Workspace with its existing identity; `/archive {}` -> ManagedWorktree with files retained.
- `DELETE /workspaces/:id/worktrees/:worktreeId` -> `{ removed:true, workspaceId }`. Only an inactive, clean, unlocked checkout with saved commit history can be removed; no force option.
- A row with `removalPending:true` and `state:'recovery'` means native checkout removal is durably confirmed while owned artifacts or final metadata still need cleanup. The UI labels the same guarded DELETE action **Finish removal**, disables Open/Archive for that row, and reuses its exact saved removal proof. It does not rerun native Git removal or delete a newer replacement path. Pending cleanup/confirmation stays visible through `409 WORKTREE_ARTIFACT_CLEANUP_FAILED`, `WORKTREE_REMOVAL_CONFIRMATION_FAILED` or `WORKTREE_REMOVAL_PENDING`; changed ownership returns `409 WORKSPACE_ARTIFACT_CLEANUP_CHANGED`.
- The top-bar workspace switcher manages worktrees. Initialization, lifetime activity guards, and native Git recovery are documented in [WORKTREES.md](WORKTREES.md).

## Git module
- `GET /workspaces/:id/git/status` -> GitStatus.
- `GET /workspaces/:id/git/status?summary=true` -> GitStatusSummary `{ isRepository, branch, ahead, behind, remote?, changedFileCount, stagedCount, changesCount, conflictCount, revision? }`, omitting complete file and branch arrays. Repository summaries carry a revision; non-repository summaries may omit it.
- `GET /workspaces/:id/git/changes?staged=true|false&limit=&cursor=&query=` -> GitFilePage `{ files, offset, total, previousCursor?, nextCursor?, revision }`. The staged selector is required. `GET /workspaces/:id/git/branches?limit=&cursor=&query=` -> GitBranchPage with `branches` and the same page metadata. Both limits default to 50 and are at most 100; query is trimmed, case-insensitive and at most 300 characters. Cursors bind the workspace, list/query, limit and revision; `409 GIT_LIST_CHANGED` requires restarting at the first page.
- `POST /workspaces/:id/git/init`.
- `GET /workspaces/:id/git/diff?path=&staged=` -> GitDiff.
- `POST /workspaces/:id/git/stage { paths: string[] }`; `/unstage { paths }`.
- Stage and unstage also accept `{ all:true }`, mutually exclusive with `paths`, to operate on the whole repository server-side and return a compact summary. ## GitHub module
- `GET /github/accounts` -> the first 30 public GithubAccount records as an array; `POST /github/accounts { token }` -> GithubAccount; `DELETE /github/accounts/:id`. The internal account directory remains complete.
- `GET /github/accounts?paged=1&limit=&query=&cursor=&selectedId=` -> GithubAccountPage `{ accounts, offset, total, nextCursor:string|null, previousCursor:string|null, revision, selected?:GithubAccount }`. Limit defaults to 24 and is at most 50. Query is at most 120 readable characters; normalized, case-insensitive terms must all match the account login/name. Account cursors bind normalized query, limit and list revision. An exact optional selected account can be returned independently of the current filter/page. Other account-list query options require `paged=1`.
- `GET /github/accounts/:id` -> exact public GithubAccount metadata, or 404 when absent. Use it to resolve a saved account outside the loaded page; absence from a page never disconnects an account or changes a repository's account selection. No token or private connection metadata is returned.
- `GET /github/accounts/:id/repos?page=` without a search or paging opt-in retains the legacy array of at most 30 GithubRepo records for that provider page. `paged=1`, a continuation cursor, or any normalized nonempty `query` returns GithubRepoPage `{ repositories, nextCursor:string|null, previousCursor:string|null, page, scanned, hasMore, searchComplete }`.
- Repository requests accept `paged=1`, `page`, `query`, `cursor` and `refresh`. Query is at most 120 readable characters; normalized, case-insensitive terms must all match the repository full name/description. Each request inspects one provider page of at most 30 repositories with the connected account's existing access, including private repositories. Page defaults to one and is at most 10,000. Signed cursors bind the account, normalized query and credential revision; do not combine a cursor with `page` or a forced refresh.
- A repository result's `page` is the provider page inspected, and `scanned` is the upstream position reached through that batch, not a total or unique-result count. Empty filtered results can still carry `nextCursor` and `hasMore:true`. Continue until GitHub stops supplying a next-page relation; only then is `searchComplete:true`. If GitHub still has another page at 10,000, the request returns `413 GITHUB_REPOSITORY_PAGE_LIMIT` instead of claiming a complete search.
- Repository `refresh=1` on a request without a cursor resets that account's repository cache; `refresh=0` does not. Invalid paging returns `400 INVALID_GITHUB_PAGE`; account list changes return `409 GITHUB_ACCOUNT_LIST_CHANGED`, and a changed connection returns `409 GITHUB_REPOSITORY_LIST_CHANGED`. Concurrent repository-fill admission can return `429 GITHUB_LIST_BUSY`. Refresh from the first page after a list/connection change.
- `POST /github/import { accountId, fullName, name? }` -> Workspace.
- `GET /github/imports/recovery` -> GithubImportRecovery[] identifies interrupted/retained imports using bounded workspace names and reasons; it exposes no credentials, temporary paths or command contents.
- Imports hold a workspace activity lease through native clone and trusted provenance commit. Failed import cleanup removes only an unchanged empty directory; nonempty or superseded workspaces remain available for recovery and return a sanitized failure instead of claiming they were removed.
- Native cloning runs in unregistered temporary storage. Publication creates files without overwriting newer visible workspace content; startup recovery never replays Git automatically.
- Canonical accounts use independent immutable connection versions containing public metadata and an encrypted PAT, with permanent disconnect markers. Legacy `github-accounts` and `github-<id>` credentials are migration inputs. Use `listGithubAccounts(ctx)` for public metadata; never read the legacy aggregate as the account directory. See [GITHUB_PERSISTENCE.md](GITHUB_PERSISTENCE.md) for concurrency, migration and reconnect behavior.
- Export `withGitCredentials(ctx, accountId, callback)` for git module using an askpass helper and clean per-command env (never token URL/global git config). Coordinate exact signature with git agent.

## Native conversations

- `GET /threads?workspaceId=&backend=&includeAgents=&archived=&query=&selectedId=&before=&after=&limit=` → ThreadListPage. `backend` is `codex-cli` (default) or `legacy`; `archived` is `active|archived`. Only one cursor direction is accepted. Browser lists are bounded to at most 60 rows and retain honest opaque cursor metadata.
- New conversation opens an unsent local draft. Its native thread is created on the first Send; no empty native thread or model request is fabricated by opening a draft.
- `POST /threads { workspaceId, title?, model?, serviceTier? }` → native Thread (201). `GET /threads/:id` reads a bounded public view; `PATCH /threads/:id { title }` uses native naming. `DELETE /threads/:id` invokes native deletion after ownership/activity checks.
- `GET /threads/:id/history?before=&after=&limit=` → Thread. Native `nativePage.nextCursor/backwardsCursor` retain actual CLI cursor identities; when item pagination is unavailable, bounded cursor envelopes also identify the native turn/item boundary inside a real turn page. Native views do not invent transcript totals or turn ordinals. The fallback reuses each fetched native turn page for a bounded group of items. Legacy views retain their separate public-history cursors. Exact first-message/missing-rollout diagnostics produce a metadata-only `nativePage.unavailable:"not-materialized"` view. Native `loaded` is observed metadata; loaded-only goals remain unavailable for unloaded threads. Empty native records cannot be silently recreated or resumed after restart.
- `GET /threads/:id/native-item-detail?turnId=&itemId=&field=&cursor=&part=&offset=&limit=&version=` inspects actual public native text/command/file-diff fields in at most 16,000 UTF-16 units. Search scans at most eight native one-item pages and returns an actual continuation cursor when needed. `cursor=` represents the first native page explicitly; later parts/offsets pin its returned cursor and public-content version. Private reasoning, raw protocol and media bytes are not returned. Legacy `/history/detail` retains its separate read-only contract.
- Reading/listing/subscribing never resumes a native thread. Explicit work mutations may resume an authorized thread; native Codex then controls its persisted queues and goals. Node never schedules or silently repeats work after an uncertain acknowledgment.
- `POST /threads/:id/run { prompt?, attachments?, fileAttachments?, clientUserMessageId?, mode?, permissionMode?, model?, reasoningEffort?, reasoningSummary?, serviceTier?, skillIds? }` → `{ threadId, turnId }` (202). Prompt limit is 64,000 characters. At least text, an image or a file is required. `mode` is `agent|plan`, `permissionMode` is `ask|full-access`; native option values are forwarded literally.
- `POST /threads/:id/input { prompt?, attachments?, fileAttachments?, clientUserMessageId?, expectedTurnId? }` → `{ threadId, turnId }` (202), using native steering with the observed turn identity. It preserves current native turn settings.
- `POST /threads/:id/queue { prompt?, attachments?, fileAttachments?, clientUserMessageId?, serviceTier? }` → `{ threadId, queuedSubmission }` (202). An explicit tier updates this conversation's native queued-work defaults before enqueueing; this is not a separate per-entry tier. `GET /threads/:id/queue?cursor=&limit=` → `{ items, nextCursor }`. The native CLI owns FIFO claim, dispatch, pause/recovery and delivery. Pending attachment receipts are not conversation history or tool authority.
- `serviceTier` is an exact bounded wire string. The composer offers `auto`, `default`, `flex`, `scale`, `priority`, `fast`, and `ultrafast` for every model; `fast` and `priority` remain distinct request values. Accepted explicit conversation tiers survive model changes, native resume, and queued starts; other conversations retain their defaults. Unsupported native/provider outcomes are returned without tier fallback. `native.requestedServiceTier` reports the site's last accepted explicit conversation choice, not provider billing telemetry.
- While a turn is active, the composer uses `GET` then `PATCH /workspaces/:workspaceId/codex/threads/:threadId/current-turn-settings` with `{ expectedTurnId, expectedGeneration, serviceTier }`. Native `turn/settings/update` acknowledges `applied` or `targetUnavailable`. This affects remaining work in the addressed turn; already-running requests and previously queued work may retain their original settings. The composer also saves the choice for the next explicitly submitted message. A changed turn or connection is never retried against a different target.
- `DELETE /threads/:id/queue/:submissionId` → `{ deleted:true }`; `POST /threads/:id/queue/:submissionId/resume {}` → `{ threadId, turnId }` (202). No custom per-entry agent options, held scheduler or fabricated queue states are added.
- Composer keys: Enter inserts a newline; Ctrl+Enter sends or steers; Shift+Enter during active work queues a future turn. The UI clears only an acknowledged draft and retains uncertain submission identities for review.
- `POST /threads/:id/stop { expectedTurnId? }` interrupts the actual observed native turn.
- `GET /threads/:id/events` → authenticated SSE. A bounded public snapshot is followed by ordered native text, public reasoning, tool activity and state notifications. Opaque SSE IDs bind the application/native process generation so restart sequences cannot suppress a fresh snapshot. Private/encrypted reasoning and raw protocol payloads are excluded.
- `POST /threads/:id/approval { approvalId, decision }` responds to the same pending native server-request ID/generation. Allowed decisions come from the live native request (`accept|acceptForSession|decline|cancel` where offered); permission requests use their native permission subset internally.
- `POST /threads/:id/answer { requestId, answers }` answers native questions, with each question mapped to `{ answers:string[] }`. Secret answers are neither cached in browser state nor copied into transcript projections. Restarted/resolved requests cannot receive a stale grant.
- `GET /threads/:id/agents` → native descendant Thread views. Child activity/approvals/questions appear inline. No separate custom agent broker or Agents panel exists.
- `POST /threads/:id/fork { lastTurnId? }` → the actual native fork. `POST /threads/:id/revert { beforeTurnId }` changes native conversation history only. Neither restores workspace files nor rewrites Git history. New custom rewind/checkpoint/Keep/Undo actions were removed; existing uncertain legacy recovery barriers remain protected.
- `POST /threads/:id/archive {}` and `/unarchive {}` use native archive operations. `POST /threads/:id/compact {}` uses native compaction.
- `GET /threads/:id/goal` → `{ goal }`; `POST` or `PATCH` accepts native `objective?`, `status?`, `tokenBudget?`; `DELETE` → `{ cleared:boolean }`. Native status/budget semantics apply, including null/omitted budget preserving an existing cap. Setting an active goal can start native work. The website does not create continuation turns.
- `POST /threads/:id/review { target, delivery?:'inline' }` starts native review. Targets are `uncommittedChanges`, `baseBranch` with `branch`, `commit` with `sha`/optional title, or `custom` with instructions. Results are native public items, not a custom finding/snapshot protocol.
- Reported usage comes only from native token-usage notifications. Current context and total usage are distinct; missing/restarted observations remain unknown. No private last-response metrics, lifetime counters or synthetic combined context window are exposed.
- Earlier `thr_…` conversations are read-only. Their model inputs, approvals, queues, goals and private data are not imported into native Codex. All write routes refuse those identities.

## Terminal module
- `GET /workspaces/:id/terminals` -> TerminalSession[].
- `GET /workspaces/:id/terminals?existingOnly=1` lists only matching retained sessions for recovery of a missing workspace. It does not create a session or regain ordinary workspace access.
- `POST /workspaces/:id/terminals` -> TerminalSession.
- `DELETE /terminals/:id`.
- WebSocket `/ws/terminal/:id` sends `{ type:'ready', session:TerminalSession, sessions?:TerminalSession[], cols, rows, truncated, flowControl?, replay:{ historyLines, historyLimit } }` before reconnect replay. The replay metadata reports the retained normal-buffer history and its configured limit. Earlier history can be trimmed while the current terminal screen remains separately represented; these limits are not an optimal-size or performance claim.
- Output frames are `{ type:'output', data:string, sequence?:number, respond?:boolean }`. Snapshot frames omit `sequence` and `respond`; live frames can designate one viewer with `respond:true` for the sequence. The server ends replay with `{ type:'replay-complete', state:TerminalReplayState, pending:string }`, using the version-1 type exported by `shared/terminal-replay.ts` and reexported from `shared/types.ts`. The browser must finish parsing snapshot output, restore this state, and parse the pending prefix before enabling input. Ordered `{ type:'resize', cols, rows }` events keep subsequent parsing at the server's dimensions.
- Client messages include `{ type:'input', data:string }`, `{ type:'resize', cols, rows }`, and `{ type:'binary', data:string }`. Binary data is a Latin-1 string of at most 64 Ki UTF-16 code units, every unit at most 255; it is converted to bytes without UTF-8 re-encoding. Emulator-generated replies use `{ type:'reply', data:string, sequence:number }`, with at most 64 Ki code units. The server accepts them only from the designated live viewer for that exact sequence and does not report them as human terminal edits. Snapshot replay must not generate replies to the PTY.
- When negotiated flow control is enabled, `{ type:'ack', characters }` counts only parsed `output.data` UTF-16 units. It excludes replay state and the pending parser prefix. The server's headless emulator answers supported terminal queries emitted while no viewer is attached; output already assigned to a live viewer does not receive a second headless answer.
- Current clients negotiate `flow=1&frames=1`, adding a 256-frame high-water limit to byte credit; older `flow=1` clients keep byte-only behavior. ACKs flush after 32 parsed frames or 16 Ki UTF-16 units. Resize arrives in the same ordered stream as output. Authority-check timeout/unavailability closes with retryable code 1013; denied/expired sessions use 1008.
- A pending control-sequence prefix is bounded to 64 Ki code units. If it cannot be restored within that bound, reconnect fails visibly while the PTY remains alive. Existing `{ type:'exit', exitCode }`, `{ type:'clear' }`, `{ type:'pong', id }` and `{ type:'error', message }` messages remain available.
- Recovery reconnects explicitly request `existingOnly=1` with a known session ID. Authentication and exact workspace/session ownership remain required; a vanished session fails visibly with no new-session fallback.
- Export `createTerminalRouter(ctx)` and `attachTerminalServer(server, ctx, authenticateUpgrade)`; authentication accepts an IncomingMessage and may return a Promise<boolean>. Complete initial authentication before upgrade or input; long-lived connections periodically revalidate without adding a filesystem read to each keystroke. Shell HOME, configuration and history remain durable under `/data`; mapped caches and runtime files use disposable storage outside `/data`. Deployment, model and password secrets are removed from the shell environment. Actual host PTY, no extra sandbox/container.

## Fixed model service and host behavior

Native Codex uses the fixed owner provider base `https://alvin3y10-api.hf.space/api`, Responses wire mode and a non-secret placeholder. The official client appends `/responses`. No TypeScript model transport, additional proxy, upstream model discovery or browser credential control is present.

Every real application start installs and verifies `@openai/codex@latest`. The executable and disposable cache stay outside `/data`; native history, SQLite/WAL state, settings and skills stay in `/data/codex-workspace/native-codex`. Updating the executable does not reset data. `/storage` retains authenticated persistence/metadata health reporting, without a Settings Storage page.

The native CLI receives server-owned host guidance and stock execution-policy rules. The host prohibits local mining, mounts, containers/VMs/emulation/manual namespace wrappers and model relays. Normal browser processes and Playwright testing remain permitted. General tunnels such as runlocal, SSH forwarding and localtunnel are allowed; cloudflared tunnels are specifically forbidden. Native browsing, browser takeover controls and realtime audio are omitted for this deployment. Resource admission/supervision uses current cgroup charge and a 90,000,000,000-byte ceiling with 2,000,000,000-byte reserve; it does not claim protection from instantaneous spikes.

Site workspace/Git/file operations retain their own dirty-buffer, conflict, ownership and activity guards. Native active work, queues, goals and background terminals prevent workspace retirement. Ordinary trash preserves native/legacy data; an explicit permanent deletion cleans only its generation-checked owned artifacts and native threads. No restart or update resets workspaces, account connections, credentials or history.
