## R14 closure after staging verification

The reviewed implementation gives native Git an unregistered scratch destination, cwd, and PWD under canonical private /tmp storage, explicitly outside the data roots. Completed content is copied into the still-owned visible workspace through the existing create-only publication helper. Application rollback still removes only a verified empty visible root. Native errors for an already spawned process wait for its actual close before the stage can be treated as exited. [Native clone](/tmp/codex-final-build/server/github.ts:549), [route lifetime](/tmp/codex-final-build/server/github.ts:765), [publication](/tmp/codex-final-build/server/github-import-staging.ts:273).

During the draft review, additional issues were corrected: the eight-import slot is reserved synchronously before asynchronous allocation, recovery metadata uses a bounded no-follow read, and a journal retired during a concurrent read is not mislabeled as corrupt. Startup recovery preserves ambiguous native-completion/ownership states and does not replay Git. The startup hook is wired after workspace initialization. [Stage admission](/tmp/codex-final-build/server/github-import-staging.ts:214), [recovery](/tmp/codex-final-build/server/github-import-staging.ts:134), [startup hook](/tmp/codex-final-build/server/index.ts:82).

The frozen source pass found no additional material source issue. The recovery DTO now includes a bounded validated name, the shared type/API contract is updated, and [GithubImportRecoveryNotice](/tmp/codex-final-build/client/components/GithubImportRecoveryNotice.tsx:20) displays sanitized reasons with stale-request and lock protection. Its refresh cannot replay an import.

R14 closes only after the behavioral reruns: the unchanged test still asserts exact user bytes after the real failed clone and now passes. The six additional staging cases also pass, including exclusive publication collision, slot reservation, unsafe temporary storage, bounded/linked journals, and actual Node exits before and after durable clone-close proof. [Preservation assertion](/tmp/codex-final-build/tests/github-import-activity.test.ts:274), [staging cases](/tmp/codex-final-build/tests/github-import-staging.test.ts:64).

## Other checked contracts

Whole-workspace restore allocates the original directory with exclusive mkdir, treats a competing empty directory as a conflict, and creates every copied leaf exclusively. It retains the complete source when copy or registration is interrupted. The activity gate covers agent, terminal, file, Git, extension, and worktree leases before physical movement. Permission errors, unsafe roots, EIO, and EACCES do not create missing-directory tombstones.

Managed checkouts remain in the native worktree lifecycle. Primary repositories with linked or unfinished worktrees cannot be moved or permanently deleted through the generic route. Missing-root metadata reconciliation does not remove surviving child checkouts or shared Git administration. WorkspaceService.remove remains metadata-only for its existing GitHub/worktree callers; those callers retain responsibility for their separately guarded native cleanup.

Restore retains the workspace ID and the current saved name/account association. Cleanup remains confined to owned native workspace/trash paths and its own state keys. It does not delete protected credentials, GitHub connections, conversations, unrelated state, or remote GitHub repositories. No new provider, filesystem mount, container, or sandbox mechanism was introduced.

Expiry uses the original deletion time plus 30 days. Startup and hourly cleanup retry eligible entries; live activity or unsafe storage can defer physical deletion. Both workspace and per-file restoration reject an expired entry while cleanup is deferred. Moving an ordinary workspace to trash no longer resets the age of its previously deleted files.

## Legacy metadata limit

Old sparse metadata omitted ordinary 0644 files and lacked workspaceFileRoots. An explicit regular-file metadata entry is reliable evidence of prior contents; new snapshots record workspace roots even when every file uses the default mode. Ordinary old registrations did not retain starter/import provenance. Names, mutable account selection, directory sizes/modes, and historical editor state cannot prove that an old missing root was nonempty at its last capture.

The old ambiguous format cannot always distinguish a truly empty directory omitted by native bucket storage from a deleted directory whose ordinary files were never recorded. The coordinator acknowledged this limit. The new field and durable exclusions protect new snapshots; this review does not claim that they reconstruct missing old contents. [Manifest compatibility](/tmp/codex-final-build/server/file-metadata.ts:121), [missing-file-root handling](/tmp/codex-final-build/server/file-metadata.ts:375).
