## Pinned image contract

The extension's model-facing name is `image_gen.imagegen`. Its arguments are a prompt and either up to five local image paths or a request for the last one to five conversation images. Supplying both reference forms fails. Without references it generates; with references it edits. These are the useful behaviors to preserve; the Rust implementation and its sandbox interfaces are not to be launched. ## Responses image wire contract

The official OpenAI documentation describes a hosted `image_generation` tool inside a normal Responses request. The top-level model remains a supported conversational model; the image model belongs to the tool configuration. Results use `image_generation_call` with base64 image data in `result`; `revised_prompt` may describe the final prompt. Image input can be supplied as base64. Explicit generation/edit action and zero to three partial images are supported configuration options. This documents OpenAI's protocol, not owner-worker availability. [Image tool guide](https://developers.openai.com/api/docs/guides/tools-image-generation), [Responses create schema](https://developers.openai.com/api/reference/resources/responses/methods/create)

| Event/item | Fields needed | Application treatment |
| --- | --- | --- |
| `response.output_item.added` containing `image_generation_call` | Item `id`, `status`, `output_index` | Create one activity at its actual place in the conversation timeline. |
| `response.image_generation_call.in_progress` | `item_id`, `output_index`, `sequence_number` | Show pending image work. |
| `response.image_generation_call.generating` | Same identity fields | Update that existing activity. |
| `response.image_generation_call.partial_image` | Identity, `partial_image_index`, `partial_image_b64`; optional format/background/size/quality | Replace the bounded preview for that call. A preview is not a completed artifact. |
| `response.image_generation_call.completed` | Identity fields only | Mark provider progress complete; this event does **not** contain final image bytes. |
| `response.output_item.done` or final `response.completed.output` image item | `id`, `status`, `result`, optional public metadata | Validate and commit the final artifact once; repeated terminal representations must deduplicate. |
| Response failure, incomplete response, disconnect or local abort | Terminal cause plus any already committed artifact | Preserve completed work; mark unfinished image activities accurately. |

The four dedicated progress events and their fields are specified in the [Responses streaming reference](https://developers.openai.com/api/reference/resources/responses/streaming-events#response.image_generation_call.completed). A final image-call item can have `in_progress`, `generating`, `completed` or `failed` status, and its result may be null. Empty or failed results must never create a successful image card. [Output item schema](https://developers.openai.com/api/reference/resources/responses/methods/create)

## Historical image implementation proposal

This original proposal is retained for its design/evidence context. The current function-helper integration and remaining verification work are stated above; its earlier “add” instructions are not a request to reimplement the wired path.

Make one hosted image tool path available to ordinary coding turns after support is established. Preserve the selected conversational model and reasoning preference. Do not automatically attach the tool to naming, compaction, review-schema, memory-extraction or other helper requests. Do not invent model answers or fall back to another endpoint when rejected. Local edit references can use the existing validated `view_image`/attachment content before the hosted call. Add an explicit reference-selection helper only if live editing shows that the direct tool cannot reliably choose the intended existing images.

The coordinator owns changes to `shared/types.ts`, `docs/API.md` and integration points, including transport, engine, history, activity UI, workspace copies and downloads. After the successful capability check, the investigator implemented the approved independent [types](../server/generated-images/types.ts), [asset service](../server/generated-images/service.ts), [preview router](../server/generated-images.ts) and [focused tests](../tests/generated-images.test.ts). The initial store cap is 8 MiB, matching the existing validator/history boundary; any increase must be coordinated across those modules. The original focused run passed all 35 cases. That evidence predates the permanent-cleanup/lease changes below; the changed candidate requires a fresh run and is not full model/UI acceptance.

1. **Transport and identity.** Add an explicit `imageGeneration` option and typed event callback beside the existing web-search contract in [transport.ts](../server/agent/transport.ts). Allowlist the image item in `cleanOutput`; retain rejection of other unsupported hosted types. Bind provider IDs, output indices and partial indices, reject conflicting identities, deduplicate repeated events and final outputs, and never downgrade a completed artifact to a preview. If asset writes occur while parsing, use an awaited, bounded sink rather than unbounded promises.
2. **Bounds that actually fit binary output.** The current parser allows 4 MiB per buffered event and 16 MiB for an entire response; image validation allows 8 MiB, and change snapshots allow 2 MiB per file. Those are separate integration constraints. Decide and test image, event, stream, disk and concurrency budgets together. A 32 MiB decoded image needs 44,739,244 base64 characters before JSON overhead; previews and a repeated final response can multiply that wire size. Do not simply remove global limits or keep unlimited full-image copies. If a smaller first-release limit is selected, display it and fail visibly without a fake success.
3. **Durable originals.** Decode canonical base64 only after checking encoded length. Validate actual PNG/JPEG/WebP structure, MIME, dimensions, pixel count and hash. Derive IDs and extensions on the server. Store an immutable original and metadata under native `ctx.config.dataDir`, with create-only files, symlink/descriptor checks and startup reconciliation of interrupted writes. The approved asset module owns its bounded metadata JSON alongside bytes rather than using the generic JSON store's unbounded read. A create-only completion marker publishes fully synced byte/metadata files without requiring native bucket hard-link support. Neither provider IDs nor provider-supplied filenames may become paths directly. Keep ordinary files unencrypted as required.
4. **Public presentation.** Persist only safe typed metadata in chat/activity snapshots: artifact ID, owning workspace/thread/message/call, state, MIME, dimensions, bytes, hash, public prompt when supplied, saved workspace path when one exists, and an authenticated preview URL. Never place result base64, opaque reasoning, protocol JSON or server filesystem paths in tool logs. Associate the image card with the existing activity timeline entry so streaming/reload order remains correct. Provide an image preview, explicit status, edit/reference action, Save to workspace and Download file using existing controls; retain phone usability and reduced-motion behavior.
5. **Workspace use and review.** Keep the original available to the saved conversation and explicit forks. Provide a create-only workspace copy operation using the current workspace path and write-admission protections. The native agent needs an actual saved path or a validated artifact-reference operation to use the image in generated code. Record successful copies in review/keep/undo; existing binary snapshots work only within their size bound. Large generated-file undo should reference the immutable original/hash and refuse to delete a changed file, rather than silently bypassing review or copying large base64 into ordinary text fields. A disk/copy failure must say generation succeeded but saving failed when that distinction is known.
6. **Model replay.** The runtime uses `store:false`; an image ID or `previous_response_id` alone is not sufficient evidence of durable replay. Persist an artifact reference plus validated provider metadata, rehydrate exact bytes from the immutable original into a schema-valid image item/content part for the next request, and verify editing after a fresh process. Extend [history.ts](../server/agent/history.ts) and compaction accounting so image bytes have a wire/storage budget, not an enormous text-token estimate. Do not redact base64: [engine.ts](../server/agent/engine.ts) currently recursively redacts ordinary result strings. Apply text redaction only to public text metadata and preserve binary integrity. Missing/corrupt originals must produce a visible unavailable-image result, never invented visual context.
7. **Cancellation and recovery.** Fence callbacks and commits by workspace/thread/run/call identity. Local Stop aborts the existing HTTPS request, prevents later previews/commits for that run and cleans uncommitted temporary files. An artifact committed before Stop remains in history. A late result must not affect a new run or workspace. Mark interrupted jobs on restart without silently reissuing a potentially billed generation. Closing an SSE reader does not establish that remote computation or billing stopped. OpenAI's separate cancellation route is limited to background responses and is outside this exact endpoint contract; do not append a cancellation URL. [Cancellation reference](https://developers.openai.com/api/reference/resources/responses/methods/cancel)
8. **Downloads.** A preview remains an authenticated application read, although its underlying native bucket is publicly readable by the user's explicit choice. A Download file action must create an immutable public download job through [DownloadService](../server/downloads/service.ts), using a server-resolved artifact ID or a safely saved workspace copy. Extend its source resolver if needed; never accept an arbitrary server path. Preserve the separate `alvin3y12/codex-downloads` bucket, direct link, 24-hour expiry/startup cleanup, blocked-fetch fallback and truthful “Download requested” wording. Expiring download copies must not delete the durable original or workspace copy. Do not auto-publish every preview to the transfer bucket.

Suggested shared metadata is a `GeneratedImage` record and a typed image event, with a relation to `ToolActivity.id`. Keep byte payloads in the server service, not `ChatMessage` JSON. Suggested authenticated app operations are preview by artifact ID, save to a chosen workspace-relative path, and create a download job. These are proposed signatures, not new API commitments. Use session validation and same-origin mutation protection for each.

Reads reject symlinks, hardlinked payloads, descriptor/path changes and digest mismatch. ### Permanent-workspace cleanup source and historical handoff

The coordinator's later lifecycle requirement adds retained uploaded images and generated originals to permanent purge. Ordinary workspace trash/restore retains originals. The authoritative `cleanupWorkspaceArtifacts` callback runs only for permanent or 30-day purge, after project/file-trash payload removal, with a frozen workspace/deletion identity and `assertCurrent()`; its original policy `mode` can still be `trash` during an eventual permanent purge. The callback already holds the workspace-removal gate.

The approved exports are `cleanupWorkspaceImageAttachments(source, workspaceId, { assertCurrent? })` from [attachments.ts](../server/agent/attachments.ts) and `cleanupWorkspaceGeneratedImages(source, workspaceId, { assertCurrent? })` from [generated-images.ts](../server/generated-images.ts). `source` can be the real `AppContext` or durable configuration only (`dataDir`/`stateDir` for uploads; `dataDir` for generated images). Config-only cleanup opens only its own storage and never resolves a live workspace, starts a cleanup timer, performs another workspace's startup sweep, or reads account/provider credentials. Root installs the callback and rechecks `assertCurrent` between subsystem leaves.

The image-only [coordination module](../server/image-assets/coordination.ts) fences matching live storage roots across contexts, cancels owned uploads/imports/retention/read leases, drains admitted work and startup recovery, and serializes duplicate cleanup requests. New and existing marker files require a successful durability sync before originals are removed. Markers are immutable empty files; legacy bounded regular markers, including torn JSON, are deny-only intent and are not deletion authority. Live memory and on-disk checks prevent late startup recovery from racing a permanent purge.

Both leaves verify workspace ownership in bounded records and validate payload hashes and descriptor/path identity before deletion. Unknown entries fail visibly, and ownership metadata remains until its associated data is gone. Failed generated rollback retains that metadata even when a byte write fails before returning its inode, so a subsequent exact cleanup can still recover. Uploaded-image cleanup streams complete retained collections with a bounded 256-record cache and repeats native directory passes to avoid skipped entries; it has no arbitrary retained-image count ceiling. Generated startup streams historical markers rather than failing at a lifetime root-entry cap.

These helpers remove original image storage only. Thread/model-input/journal/fork copies of image data are owned by the separate conversation-state cleanup. Existing independently exported public download copies remain under their separate 24-hour lifecycle.

## Native realtime contract and its boundary

The following protocol research is historical reference. Realtime is now explicitly excluded by the user after the verified capability check; none of the audio architecture or acceptance ideas below is current release work.

Pinned `RealtimeConversationVersion` defaults to V2. V2 creates a real session with 24 kHz PCM input/output, near-field noise reduction, server voice activity detection, optional input transcription, and text or audio output. Its `background_agent` function routes user requests into Codex and supports steering ongoing work; `remain_silent` prevents unwanted speech. These are session tools, not a transcription endpoint. V1 uses the older conversation/handoff form; V3 uses the frameless Live-style client-delegation form. Their serializers must not be mixed. [V2 configuration](https://github.com/openai/codex/blob/78245b47af2a7aafcabe025828ceecca69db4df1/codex-rs/codex-api/src/endpoint/realtime_websocket/methods_v2.rs), [V3 configuration](https://github.com/openai/codex/blob/78245b47af2a7aafcabe025828ceecca69db4df1/codex-rs/codex-api/src/endpoint/realtime_websocket/methods_frameless_bidi.rs)

Upstream starts WebSocket sessions or creates WebRTC calls from an SDP offer and attaches a server-side sideband using the returned call ID. It appends audio, text and speakable responses, handles agent handoffs and interruption, and persists session/transcript/promoted-agent-item/close facts for interleaved history. The WebRTC call path is `realtime/calls` for V1 and `live` for V3; upstream rejects AVAS WebRTC V2 rather than pretending the formats are interchangeable. [Call creation](https://github.com/openai/codex/blob/78245b47af2a7aafcabe025828ceecca69db4df1/codex-rs/codex-api/src/endpoint/realtime_call.rs), [Conversation runtime](https://github.com/openai/codex/blob/78245b47af2a7aafcabe025828ceecca69db4df1/codex-rs/core/src/realtime_conversation.rs)

Official Realtime WebSocket sessions exchange `session.update`, audio-buffer input, output audio/transcripts, function calls and lifecycle events. WebSocket clients must manage playback and truncate unplayed audio on interruption; WebRTC media has different playback handling. Current GPT-Live documentation likewise starts a separate Live session even when reasoning is delegated to Responses. Responses WebSocket mode instead sends Responses-create bodies over a persistent connection. The transport name alone does not make these protocols equivalent. [Voice WebSockets](https://developers.openai.com/api/docs/guides/voice-websockets), [Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations#handling-interruptions), [Responses WebSocket mode](https://developers.openai.com/api/docs/guides/websocket-mode)

File transcription, live transcription, speech generation and speech-to-speech conversation are separate capabilities. A transcription-only microphone button can be useful, but it does not establish realtime conversation or agent-handoff parity. Browser speech recognition may use a browser-vendor service; it must not silently bypass fixed model routing. [Audio workflow distinctions](https://developers.openai.com/api/docs/guides/audio)

There is also a distinct upstream static audio-attachment contract: `{"type":"input_audio","audio_url":"…"}` inside message/tool content, with local WAV/MP3/M4A/WebM/OGG conversion. That is not the realtime session protocol. The fetched public Responses-create reference does not describe this content field, and the owner worker's support remains untested. Consequently this investigation does **not** conclude that Responses can never accept audio. [Pinned audio content model](https://github.com/openai/codex/blob/78245b47af2a7aafcabe025828ceecca69db4df1/codex-rs/protocol/src/models.rs#L878)

### Current endpoint decision — realtime excluded

The exact authorized `/api` route is demonstrably a Responses route in the public relay. A documented HTTP Responses request does not supply the realtime session handshake or bidirectional media contract above. The public relay contains no adapter implementing those semantics, and its worker implementation is unavailable here. This identifies a concrete contract gap; it is not evidence that the owner can never support one.

The bounded exact-route check in [REALTIME_CAPABILITY.md](REALTIME_CAPABILITY.md) is complete: HTTP 101 was followed by rejection of documented `session.start`, with the server requiring `response.create`. The inspected relay revision `7ea650d…` maps both HTTP and WebSocket to `/v1/responses`. Apply the user's instruction to omit unsupported realtime audio. No owner-worker contract request, new endpoint, voice control or release-blocking audio probe remains. Do not guess `/audio`, `/realtime`, `/live`, `/models`, change domains, add a proxy or enable provider/key controls.

The original hypothetical architecture below is preserved only as historical reference, not an implementation or QA assignment:

- A thread-scoped Node session manager with a fresh session/run identity; bounded media queues; server-owned credentials; authenticated browser WebSocket and live session revocation; idle/total duration limits; and explicit close/error recovery.
- Browser microphone permission on deliberate Start, format-correct capture/resampling, bounded ordered playback, mute/stop and interruption controls, visible captions, and no retained raw audio by default. Stop/lock/logout/workspace deletion must release tracks and playback. A session from a previously selected workspace must never mutate the new workspace's state.
- An adapter for the evidenced protocol version: real session readiness, audio input/output, transcript finalization, cancellation/truncation, and terminal events. Do not mark a socket open as a successful voice session.
- A `background_agent` bridge into the existing real engine/steering/approval/question paths, with all host prohibitions in voice and coding instructions. Only public permitted text/results return to voice. Keep child task isolation and inline approvals; do not expose private or encrypted reasoning to speech.
- Durable finalized transcript/session/agent-item facts in the actual conversation order. On process replacement mark a live session interrupted, retain completed history and require a deliberate new Start rather than secretly activating a microphone.

An offline speech frontend coupled to Responses would be a different implementation requiring its own resource, licensing, privacy and acceptance decisions. It must not be introduced silently or reported as proof that the upstream Realtime API works through this relay.
