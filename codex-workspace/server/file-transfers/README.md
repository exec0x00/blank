# Native workspace transfers

`transferNativeEntry` copies files and folders through the existing native filesystem. It does not start a proxy, mount anything, launch commands, or stage file payloads elsewhere. The implementation deliberately uses create-only destination entries even on filesystems where ordinary rename succeeds: Node's `fs.rename` does not offer a no-overwrite flag. Small sibling and cross-parent directory renames were observed to work on the deployed native bucket; these observations do not establish collision or concurrent-writer safety.

Each operation checks paths through open directory descriptors, copies regular bytes through a 256 KiB buffer, and preserves symbolic links as links. It verifies complete source and destination trees, including content hashes, identities, modes, and unexpected entries. Move removes only captured, still-matching leaves and empty directories, rechecking destination bytes before removing the corresponding source. It never runs recursive removal against a partially changed source or destination. A failed operation can leave a partial destination or a partially removed source; these locations stay available for inspection. Selections containing multiple hard-linked names for the same object are rejected before a Move writes payloads; Copy can duplicate their contents.

The limits are 50,000 entries, 32 GiB of regular file contents, 96 path components, 32 MiB of manifest JSON, and a 30-minute operation deadline. Directory iteration, manifest paths, recovery scans, public response bodies, redirects, and network retries have additional bounds. At most two transfers are admitted at once. Production checks fresh cgroup-aware resource accounting and the shared 90 GB ceiling with a 2 GB reserve before work. Admission forecasts possible source and destination cache growth from the captured byte total; later checks occur after 16 MiB of I/O or five seconds. This admission check does not control memory allocated by unrelated processes.

`transferWorkspaceEntry` adds ordinary JSON recovery records under the configured durable state directory. A small `file-transfer-<id>.json` record precedes copying. A verified `file-transfer-tree-<id>.json` manifest containing relative paths, hashes and identities precedes source removal. Successful transfers remove their records; validation failures before payload writes retire only an unchanged record. Genuine interrupted records remain bounded and visible through the workspace recovery-status route. Startup only marks abandoned operations interrupted. It does not resume deletion, retry copies, remove partial destinations, or act on saved manifest paths.

When `requirePersistentData` is enabled, the service requires its metadata checkpoint callback. It uses direct, unauthenticated public Hugging Face GETs to hash every destination file and confirm the transfer manifest, journal, and filesystem metadata. It confirms the removal-intent journal before any source unlink. After removal, fixed-origin HEAD checks confirm that old regular-file objects are absent, then another filesystem metadata checkpoint and public readback precede success. Local `fsync` alone is not treated as a bucket upload receipt. Provider response bodies and signed URLs never become error messages.

WorkspaceService file mutations, including editor saves and ordinary agent file writes, share a queue keyed by storage directory and workspace ID; the existing workspace activity lease prevents workspace removal while a transfer is active. Editor saves must also preserve their expected-version check and frontend transfer guard. External commands and already-open file descriptors cannot be atomically excluded by POSIX path checks: an uncooperative writer can still race the final check/unlink interval. The service conservatively stops on observed changes and retains recovery evidence; it does not claim a filesystem-wide lock or an atomic directory transaction.

Other native write integrations can use `withWorkspaceFileMutation(workspacesDir, workspaceId, operation)` from `queue.ts`. Wrap only direct filesystem work; calling a mutating WorkspaceService method inside that callback would acquire the same queue twice. Workspace read/resolve methods do not acquire it.

The optional fourth argument `{ signal }` cancels only that caller. A queued caller rejects promptly and its callback will not run, while its ordering barrier remains until earlier work finishes. Once a callback starts, the returned promise and activity lease remain held through its actual cleanup, even after cancellation; the callback must cooperate with its signal. There is no global queue shutdown. `PublicBucketVerifier` also accepts a caller signal, propagates it to GET/HEAD requests, clears its native retry timer on cancellation, and preserves the caller's abort reason. Injected hooks are still awaited when they ignore cancellation so context owners can report a truthful drain timeout.

Tests exercise actual local files, directories, symlinks, streamed writes, API routes, independent service instances, and restart-style recovery. Injected write/unlink/transport faults verify failure behavior. Local tests and controlled HTTP fixtures do not prove deployed bucket durability; deployment must separately exercise the new application endpoints and verify their public objects and remount behavior.
