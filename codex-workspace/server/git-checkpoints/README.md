# Git checkpoints

This module saves immutable `before`, `after`, and rollback `backup` snapshots for the requested conversation file rewind. It does not perform a live workspace restore. The rewind coordinator attributes changed paths from consecutive before/after pairs, rejects manual edits and repository identity changes, and supplies verified materials to its guarded file transaction.

The pinned Codex source at `78245b47af2a7aafcabe025828ceecca69db4df1` has **removed** the GhostCommit/undo feature (`codex-rs/features/src/lib.rs`) and marks ghost snapshot configuration as legacy no-ops (`codex-rs/core/src/config/mod.rs`, `codex-rs/config/src/config_toml.rs`). Its remaining `git-utils/src/baseline.rs` constructs raw blob/tree baselines for disposable repositories. Its function that deletes repository metadata is not used here. This feature is a new implementation, not a claim that current Codex still produces ghost snapshots.

`GitCheckpointService.capture` validates the registered repository or managed worktree, reads its exact real index, and uses a disposable index outside durable storage for read-only Git enumeration. Read-only native plumbing receives pinned root/Git/common-directory descriptors, no inherited credentials, no lazy fetch or allowed transport, and disabled fsmonitor/hooks. No `add`, `reset`, `checkout`, `clean`, `commit`, `update-ref`, or network command runs against the source repository. Raw source bytes bypass attributes and filters.

Repository identity persists through normal instance replacement and reconstruction of the native `/data` files. The first capture creates one signed, create-only `.codex-workspace-repository-v1.json` marker inside the validated common Git directory. Managed worktrees also get `.codex-workspace-checkout-v1.json` inside their own validated Git administration directory. These fixed app-owned files bind random repository/checkout generations to exact workspace IDs, registration creation times, worktree IDs and canonical paths; they do not edit source `HEAD`, index, configuration, hooks or refs. Missing, invalid or transplanted markers cannot authenticate an earlier checkpoint.

Historical comparisons use those durable generations and exact branch/HEAD/object-format identity. Device/inode observations remain in each manifest with a live observation nonce. Active services sharing the same durable storage scope retain bounded directory descriptor leases (512 process-wide), preventing inode recycling from erasing replacement evidence. Every filesystem read/write also pins its current descriptors. Callers drain operations and await `close()`; leases release only after all service instances sharing that scope close, and a later scope receives a fresh nonce. Across a fresh process or complete service restart, inspection may accept reconstructed physical directories with the same signed logical identity and exact file/index history chain. Old preview/commit evidence never crosses that boundary: the live comparator requires the same nonce and physical observations, so the user must obtain a fresh preview. Recovery does not replay old inode numbers as mutation authority. The reconstruction tests copy only owned fixtures into replacement directories and launch a fresh Node process; they do not mount anything or claim to be a live HF remount test.

The immutable checkpoint is an independent native Git repository under `stateDir/git-checkpoints-v1/<workspace>/<checkpoint>`. It contains ordinary Git blobs, trees and a parentless commit. Its detached `HEAD` and create-only `refs/codex/checkpoint` both identify that commit; a symbolic HEAD outside `refs/heads/` would fail native Git validation. Its working tree, exact raw index, and currently indexed stage blobs remain reachable. A signed manifest binds workspace/thread/turn/phase, source repository identities, HEAD/branch, full ordinary Unix permissions, symlink target bytes, raw hashes and the exact index semantics. The independent object store always uses SHA-1; source repositories and index checksums may use SHA-1 or SHA-256. Snapshot commands receive no account credentials, and metadata adds no tokens or remote URLs. Source bytes follow the documented repository coverage.

Every capture is all-or-unavailable within explicit coverage. Defaults are 5,000 paths, 16 MiB per file, 128 MiB combined working/index/staged material, 8 MiB metadata/index, and 120 seconds. Captures account for cgroup memory with the shared 90,000,000,000-byte ceiling and 2 GB headroom, forecast transient buffers/file cache, and check available storage when the backing filesystem reports capacity. Git-ignored untracked files and empty directories are excluded; tracked paths remain included even when ignored. Special files, hard links, special permission bits, nested repositories/submodules, unsupported encodings, split indexes and sparse indexes fail explicitly. Optional raw index extensions are preserved; selective restore must reject unsupported semantic extensions such as REUC, whose additional former-stage objects are not independently retained here.

`read` authenticates the immutable manifest and native root commit/ref. `readBlobs` validates all requested raw materials with their native Git IDs, SHA-256 hashes and source index object IDs in one bounded batch; `readBlob` is the single-item convenience form. `inspectCurrent` reads every previously captured path, including paths now ignored or missing, plus current candidates. Its token includes current bytes/kinds/modes, index identity, logical/physical repository identity, observation boot, branch and HEAD. These reads never perform restoration or delete user files.

Before publication, captures recheck working-file identities, raw index, HEAD and untracked enumeration. This detects concurrent edits conservatively; it is not a filesystem freeze. Callers must hold the shared file mutation queue for restore and recheck current inputs immediately before writes. The source file transaction must still guard uncooperative external writers. `capture` and `cleanupThread` themselves acquire the shared queue, whereas `read`, `readBlobs`, `inspectCurrent`, and `assertRepository` do not acquire it and can be used within a transaction.

There is no destructive startup replay. Incomplete or corrupt snapshots remain unavailable after restart. Per-workspace retention stops new capture at 256 snapshots or the 2 GiB durable budget, preserving existing snapshots instead of silently dropping a turn's rewind. Explicit `cleanupThread` removes only signed, namespace-constrained owned records, optionally retaining specified turn IDs. Before deletion it publishes and verifies a signed `.delete-<checkpoint>.json` intent beside the record, bound to its exact capture owner. That proof survives removal of the record's final owner file and directory. Retry may finish an authenticated ownerless **empty** directory or an already-absent record; unknown/nonempty entries, aliases and changed owners remain untouched. The intent is removed only after verified directory absence. Reads reject a deleting checkpoint with `CHECKPOINT_DELETING`; quota scans authenticate pending intents without resuming them. The reviewed workspace deletion/expiry job uses `cleanupWorkspaceGitCheckpoints` inside its existing exclusive barrier, preserving its retry journal until completion. Exact-thread maintenance uses `cleanupThreadGitCheckpoints` only after quiescing that family and proving surviving references, before removing canonical thread/operation authority; it does not reacquire the caller's gate. No cleanup resets the live repository or sweeps temporary directories. Each scan removes only its own disposable index/directory after completion.

Focused tests in `tests/git-checkpoints.test.ts`, `tests/git-checkpoint-index.test.ts`, `tests/git-checkpoint-cleanup.test.ts` and `tests/git-checkpoint-identity.test.ts` use owned native Git/FS fixtures, including independent `git fsck`, SHA-256 and v4 indexes, managed worktrees, exact staging, modes/symlinks/binary data, a fresh Node reconstruction, live token expiry, descriptor lifetime, interrupted deletion, tampering, concurrency and honest unsupported cases. See test execution reports for actual validation; source authoring alone is not a passing gate.
